1. INTRODUCTION                                          *yap-introduction*

yap is an LLM chat plugin where the conversation lives in a plain, editable
markdown buffer. A small Go binary (`yap`) handles provider requests and the
agent/tool loop: it reads the messages on stdin and streams the reply to
stdout. There is no TUI and no hidden conversation state between turns.

To install: build the binary and put it on Neovim's PATH (see the README),
configure a provider in ~/.config/yap/settings.json, then
`require("harness").setup({...})` and run `:Yap`.

Because the buffer is the conversation, ordinary editing changes it:

- Deleting a region removes it from the conversation (branching).
- Editing an assistant reply changes what the model "said".
- Writing your own `# @assistant` message steers the model (prefill).
- Yanking, undo, folds and rendering are just Neovim; `:undotree` is a
  branch navigator.

2. SETUP & CONFIGURATION                                *yap-configuration*

Lua setup (example; substitute your own model groups): >lua

  require("harness").setup({
    bin = "yap",                  -- path to the Go binary
    system = "You are a helpful coding assistant. Answer concisely.",
    agents_file = vim.fn.expand("~/.config/yap/AGENTS.md"),
    agents_dir = "~/.config/yap/agents",       -- subagent definitions
    sessions_dir = "~/.config/yap/sessions",   -- sessions + scratch + audit logs
    templates_dir = vim.fn.expand("~/.config/yap/templates"), -- insert() files
    skills_dir = vim.fn.expand("~/.config/yap/skills"),       -- system-prompt files
    notify_done = true,           -- vim.notify when a hidden turn finishes
    builtin_completion = true,    -- false when cmp/blink owns completion
    model_groups = {              -- named model tiers (provider/model combos)
      agent = "openai/gpt-6.1-sol", -- new sessions, including :YapEval
      flash = "deepseek/deepseek-flash", -- :YapEval! and session titles
    },
    nerd_font = true,             -- false for plain-Unicode icons
    icons = { since = "󰅐", total = "󰆼" }, -- winbar/picker glyph overrides
    keymaps = { stop = "<C-c>" }, -- override any key; "" disables it
  })
<

`agents_file` is the system prompt for new buffers, read per buffer (edits
apply to the next session). When missing or empty, `system` is used. Like the
other data paths, a leading `~` resolves against your home directory; a
relative path is refused. The default is
`$XDG_CONFIG_HOME/yap/AGENTS.md` (or `~/.config/yap/AGENTS.md`).

`agents_dir` and `sessions_dir` locate yap's data under the XDG config home —
`$XDG_CONFIG_HOME/yap/` (default `~/.config/yap/`); a leading `~` resolves
to your home directory, an absolute path is used verbatim.

`notify_done` (default true) fires `vim.notify` when a turn completes in a
buffer not visible in any window. The turn's `turn_end` payload (model,
tokens, cost, ms) is also emitted on the `User YapTurnDone` autocmd so other
plugins can hook completion (e.g. noice/nf-notify rendering, or chaining a
next send). Disable with `notify_done = false` and hook that event yourself.

`builtin_completion` (default true) enables Neovim's native LSP completion
popup for Yap sessions. Set it to false when using nvim-cmp or blink.cmp; the
language server still serves their completion requests, symbols and
diagnostics. See |yap-lsp| for the optional completion source.

`nerd_font`/`icons` control the winbar and picker glyphs (|yap-winbar|).
Icon keys include `since`, `total`, `cache`, `running`, `waiting`, `stopped`,
`error`, `idle`, `done`, `steer`, `queue`, `clear`, `approval`, `cap_l`, `cap_r`. Defaults are
Nerd Font v3 glyphs; `nerd_font = false` selects plain-Unicode icons, the
typographic spinner and the block gauge. Explicit `icons` entries win; set one
to `""` to drop it.

`model_groups` has two tiers. `agent` starts regular conversations, including
`:YapEval` sessions. `flash` handles one-shot, no-tools `:YapEval!` edits and
short session titles (the initial label and updates after each turn). Set
`flash = ""` to disable automatic titles and use `agent` for `:YapEval!`.
Rename `session.md` to give the session a permanent title; descriptions are
regenerated automatically after every turn and are only a label, never an
title you can set by hand. A renamed transcript shows its filename in every
session view.
The per-session |change_model()| picker discovers available models through
`yap models`, which queries configured backend providers with their current
credentials. It does not change the configured default for new sessions. The
row is just the combo name; the preview shows that model's rate per 1M tokens
(input, output, cached input) and its context window, so an accidental switch
to a top-tier model is visible before it costs anything.

`price_guard` is the same information as a speed bump. Before a turn is sent,
`stream.send()` prices it as `context x 2 steps x the model's uncached input
rate` and, when that exceeds `max_usd`, asks once:

```lua
price_guard = { enabled = true, max_usd = 2.0 },  -- default
```

"Send anyway" approves that model for the rest of the session, so a repeated
expensive turn does not ask again; switching model re-arms it, because the
approval is keyed by combo. A subagent is never blocked (nobody could answer),
and a model missing from the price catalog is never guessed at. The estimate
errs high on purpose — caching only makes the real bill smaller — and the audit
log, not this number, is the accounting record.

`keymaps` maps each action in |yap-keymaps| to its key; set one to `""` to
disable it. `templates_dir`/`skills_dir` configure
|yap-templates|.

Config and data files (defaults shown; the config home is
`$XDG_CONFIG_HOME/yap` — `~/.config/yap` unless `$XDG_CONFIG_HOME` is set —
and each path is configurable via `setup()`):

  ~/.config/yap/settings.json   Providers: >json

  {
    "providers": {
      "moonshot": {
	"base_url": "https://api.moonshot.ai/v1",
	"api_key_env": "MOONSHOT_API_KEY"
      }
    },
    "sandbox": {
      "enabled": true,
      "allow_write": ["~/.cache"],
      "deny_read": ["~/private"]
    }
  }
<
  Supported providers (the provider name is the key under "providers"):

    name        base_url                                  api_key_env example
    openai      native; default https://api.openai.com/v1  OPENAI_API_KEY
    anthropic   native; default https://api.anthropic.com  ANTHROPIC_API_KEY
    google      native; default Google Generative Language GEMINI_API_KEY
    gemini      alias of google                            GEMINI_API_KEY
    deepseek    native; default https://api.deepseek.com   DEEPSEEK_API_KEY
    <other>     REQUIRED; any OpenAI-compatible endpoint   e.g. MOONSHOT_API_KEY,
                (moonshot https://api.moonshot.ai/v1,      OPENROUTER_API_KEY
                openrouter https://openrouter.ai/api/v1,
                z.ai, local servers, ...)

  Native providers need no `base_url` (set one only for a proxy; Anthropic's
  takes no `/v1`, Google's no `/v1beta`). Direct Anthropic ids use dashes
  (`claude-sonnet-5-5`), OpenRouter's dots. API keys come from the named env
  vars; API keys come from the named env vars. Prices come from
  `agent/price/pricing.json`.

  A provider can authenticate with a subscription login instead of an API
  key: set `"auth"` to a login method (`"chatgpt"` today) and drop
  `api_key_env`. `yap login [METHOD]` runs the browser sign-in once; login
  methods self-register, so adding one needs only a new file in agent/auth.

    {
      "providers": {
        "openai": { "auth": "chatgpt" }
      }
    }

  The `chatgpt` method charges requests to a ChatGPT Plus/Pro plan through
  OpenAI's "Sign in with ChatGPT" flow, authorized once with
  `yap login chatgpt` (~/.config/yap/chatgpt.json, mode 0600, access token
  refreshed automatically). Requests go to the public Responses API with the
  same model ids as an API key (`gpt-5.4`); `store` is forced to false, as
  that route requires. Manage how much of the plan yap may use in ChatGPT
  settings → Usage → App limits. `yap login chatgpt` again to reauthorize, or
  delete the file to forget the account.

  All auth methods serialize login and token renewal across Yap processes.
  Each method uses a persistent lock file under the Yap config directory;
  waiting requests can be canceled, and process exit releases the lock.
  Restart existing backends after upgrading so they also use this locking.

  The `mcp` block configures external MCP servers, whose tools are exposed to
  the model as `mcp_<server>_<tool>`. Each entry is a stdio server (a local
  `command`, optional `args` and `cwd`) or an HTTP server (`url`). Credentials
  never appear literally: `env` maps a child variable name to a Yap env var,
  and `headers` maps an HTTP header to a Yap env var. A header value may carry
  a literal scheme prefix, e.g. "Bearer CENSYS_API_KEY" sends
  `Authorization: Bearer <value>`. `tools` optionally lists
  which of the server's tools to expose (omit for all). `lazy` (default
  false) defers a server's tool definitions: it exposes a single `mcp_<server>`
  loader tool whose description summarizes what the server offers, and the
  definitions enter context only once they are needed. Calling a listed tool
  directly also works: the call activates the server and then runs, so a lazy
  server never costs a round-trip. Activation persists for the session's
  backend, and changing the server's config re-arms it. Use
  it for situational servers (a debugger, reverse-engineering tool, ...)
  whose definitions would otherwise bloat every turn's context. >json

    {
      "mcp": {
        "exa": {
          "url": "https://mcp.exa.ai/mcp",
          "headers": { "x-api-key": "EXA_API_KEY" }
        },
        "github": {
          "command": "github-mcp-server",
          "env": { "GITHUB_TOKEN": "GITHUB_TOKEN" }
        }
      }
    }
<
  MCP servers stay connected for the backend's lifetime; a stop() cancels the
  in-flight call without closing them. MCP calls are not guarded by the
  static gate: their reach is whatever the server and its credentials
  permit. A server can still gate its own side effects by asking for
  approval — its MCP elicitation request is routed through the same
  Run/Deny the guard gate uses (accept = approve, decline = deny), so a
  server that prompts (ssh-mcp's destructive and privileged commands) parks
  the turn for the human rather than running.

  The `sandbox` block configures the bash tool's bubblewrap sandbox (Linux
  only; see |yap-sandbox|). `enabled` defaults to true — the sandbox is on
  unless the file sets `enabled: false`; on a machine without bubblewrap
  (or off Linux) it silently falls back to running bash unsandboxed.
  `allow_write` adds directories to the writable allowlist beyond the
  always-writable project dir (the live |:pwd|, so it follows |:cd|) and the
  session's assets dir — the same allowlist that bounds the `write` and
  `edit` tools. `deny_read` adds paths to shadow with empty mounts beyond the
  built-in secret directories (`~/.ssh`, `~/.gnupg`, `~/.aws`, `~/.config/sops`,
  `/etc/ssh`, `/run/agenix`), which are always shadowed so bash cannot read
  them.

  ~/.config/yap/AGENTS.md  Default system prompt (see above).
  ~/.config/yap/templates/ insert() template files (|yap-templates|).
  ~/.config/yap/skills/    insert() skill files (|yap-templates|).
  ~/.config/yap/sessions/  Sessions, scratch buffers, audit logs and assets.
  ~/.config/yap/agents/    Subagent definitions.

3. COMMANDS                                                  *yap-commands*

Commands act on the current buffer unless otherwise noted. They are quiet on
success: visible edits, the winbar and pickers confirm ordinary actions.

*:Yap*
:Yap [path]           Open a new session buffer with a system message and an
                        empty `# @user` prompt. Nothing is sent until you type
                        there and send().
                        With no argument the session lands under the sessions
                        root as usual. With a file path (or a directory, which
                        gets `session.md` inside it) the transcript is created
                        there instead — a portable session whose audit log and
                        assets live in a central `data_dir` (|yap-sessions|).
*:YapClear*
:YapClear [keep]      Replace the result bodies of all but the last [keep]
                        (default 2) yap:tool regions with a one-line
                        placeholder naming the audit-log lines
                        (path:line-range) where the removed output lives.
                        Full output stays in the audit log (|yap-audit|).
                        While a turn is running, :YapClear queues the clear
                        to run when that turn completes (a broom icon shows
                        in the winbar); a second :YapClear cancels it.
*:YapCompact* *yap-compact*
:YapCompact [instructions]
                        Insert the built-in compact prompt, append any custom
                        instructions, send, and — once the summary has
                        streamed in — offer to delete the superseded history.
*:YapEval*
:YapEval [instruction]
                        Open an interactive eval session in a split about
                        the selected lines (or about the current file with no
                        range). It is a regular session (default system
                        prompt, tools, follow-ups). An eval without a selection
                        or instruction stays out of saved history until you
                        add a prompt or complete a turn.
                        The selection is quoted as context and the
                        source buffer is never changed. With an instruction
                        the first turn is sent at once; without one the
                        cursor waits in the user turn for your question.
:YapEval! [instruction]
                        Replace the selected lines with the model's output: a
                        one-shot, no-tools call to `model_groups.flash` (or
                        `agent` when flash is empty). Acts on a linewise range
                        (a visual selection via `:'<,'>` or an explicit
                        `:1,5`); with a selection and no instruction it
                        applies a default transform ("Improve this text"),
                        and with no range it prompts for an instruction. In a
                        yap buffer the replacement is wrapped as a single
                        `# @assistant` message (select a run of turns to
                        summarize them); in any other buffer it is plain text
                        (refactor a function in place). With no range, the
                        output is inserted at the cursor as new lines
                        (generate content into a fresh, empty buffer). No
                        default keymap for either form.
*:YapFork*
:YapFork [name]       Copy the current in-memory conversation into a new,
                        independent session in the same project. The original
                        buffer, file and running state stay attached to the
                        original; the copy opens in the current window. No
                        name generates a filename; a name uses `name.md`.
                        Existing files are never replaced.
LUA API                                                  *yap-lua-api*

The per-buffer actions below are Lua functions on `require("harness")`; there
are no `:Yap...` commands for them. Bind them to keys or call them directly:
>lua

  require("harness").send()                 -- send the transcript
  require("harness").stop()                 -- stop the in-flight request
  require("harness").live()                 -- open the live tool tail
  require("harness").guard()                -- open/close the guard board
  require("harness").insert(name)           -- insert a template / merge a skill
  require("harness").change_model(combo)    -- set this session's provider/model
  require("harness").sessions()            -- pick a saved session (current project)
  require("harness").sessions("all")       -- pick a saved session from any project
  require("harness").symbols()             -- pick a document symbol (newest first)
<
`sessions(scope)` lists saved sessions: `"cwd"` (the default, current
project) or `"all"` (every project under the sessions root). `insert(name,
{ at_cursor = true })` inserts the raw file at the cursor instead of
appending/sending. See |yap-keymaps| for the default shortcuts that call these.

4. KEYMAPS                                                    *yap-keymaps*

Set only in yap buffers, except +, g+ and <leader>g, which are global. Every binding is a `keymaps` config key
(see |yap-configuration|); the defaults are shown below.

  <C-s> (n, i)          Send the buffer. The reply streams in.
  <C-c>                 Finish the current response and tool calls, then stop
                        before another model step. While it unwinds, the
                        winbar shows a stop icon beside the spinner; press
                        again to terminate its backend and running tools.
  <leader>m             Change model (picker, see change_model()).
  <leader>g             Open/close the guard board (see guard()).
  <leader>l             Watch the live tool tail (see live()).
  <leader>s             Pick a document symbol: messages newest-first, then the
                        frontmatter block at the bottom (see symbols()).

Inside the guard board, <leader>l opens the live tail directly below it;
inside the live tail, <leader>g opens the guard board directly above it.
Both bindings are present in every yap panel (session, guard, live tail and
scratch), so the two stay stacked in the fixed session → guard → log order
regardless of which one you open first.
  <leader>j             Toggle the scratch buffer (see |yap-sessions|).
  <C-Enter> (n, i)      Pick a template (see insert()). A template is inserted
                        and sent; to merge a skill, call insert(name) instead.
                        In scratch, insert the raw file at the cursor instead.
  +                     Pick a saved session to resume (current project).
  g+                    Pick a saved session from any project.
  g?                    Show the current Yap shortcuts in a searchable
                        floating window; use `/`, `n` and `N`.
  <Tab>                 Toggle the fold under the cursor.
  ]m  [m                Next / previous message heading.
  ]u  [u                Next / previous user message.
  ]a  [a                Next / previous assistant message.
  ]t  [t                Next / previous tool call or thinking region (opens it).
  ]c  [c                Next / previous thinking region (opens it).
  ]e  [e                Next / previous error region (opens it).
  ]]  [[		Next # heading (default Neovim markdown behavior)

  <leader>1             Fold all agent messages; user prompts stay open.
  <leader>2             Fold all tool calls and thinking regions.
  <leader>3             Unfold everything.

  Text objects (operator-pending and visual mode):
    im / am             inner / a message — the body without its `# @role`
                        heading, or the whole message. `cim` replaces a
                        message body; `dam` drops a message.
    it / at             inner / a thinking, tool or error region — the content
                        without its markers, or the whole region.

View 2 is the default; the system prompt stays folded in views 1 and 2
(|yap-folding|).

5. BUFFER FORMAT                                                *yap-buffer*

A yap buffer is plain markdown. Headings delimit messages: >

  # @system
  # @user
  # @assistant
<

Everything between headings is message content. Everything before the first
heading is ignored by the parser — that is where the session's state lives,
as YAML frontmatter: >

  ---
  description: Fix session picker labels and summaries
  model: kimi-k3
  provider: moonshot
  created_cwd: ~/code/project
  turns: 14
  created_at: 2025-09-29T19:22:33Z
  updated_at: 2025-09-29T19:24:01Z
  models:
    - moonshot/kimi-k3
    - deepseek/deepseek-v4-pro
  tools:
    - read
    - search
    - glob
  ---
<

`description` is the generated summary, refreshed after every turn; it is a
label for the conversation, not a title — yap regenerates it, so a hand edit
stays only until the next turn. The transcript filename is the session's
permanent title: rename `session.md` with |:file|, |:saveas| or your file
explorer, and views show that filename instead of the description. The rest
of the frontmatter:

  `provider`/`model`      The combo to resume with.
  `created_cwd`           The exact directory the session was created in.
  `models`                The combos used, most recent last.
  `tools`                 The per-session tool allowlist. Remove a line to
                          retract that tool on the next send.
  `turns`                 Completed `# @assistant` replies, so the picker can
                          show depth without opening the file.

`forked_from` and `subagent_parent` record the session's single parent as its
directory (not its transcript filename), so a |:file| rename never breaks the
link. A fork always nests under its parent in the saved picker; a subagent
nests only while its parent is open, keeping an inactive conversation's row
lean.

The active combo is the buffer's own: read from the frontmatter when the
session is opened, set by change_model(), else `model_groups.agent` for a new
session.

6. MARKERS & TOOL REGIONS                                      *yap-markers*

HTML comment regions of the form `<!-- yap:<word>` ... `-->` appear in the
buffer but are never sent to the provider as buffer text:

  <!-- yap:thinking   Provider-exposed reasoning (or summaries), streamed in.
                        Folded away with the assistant message.
  <!-- yap:error      Backend error record, left after a failed send.

Tool regions                                                *yap-tool-region*

A tool call and its result are ONE region inside an assistant message: >

  <!-- yap:tool {"id":"call_1","name":"edit","arguments":{...}} -->
  Successfully replaced 1 edit(s) in main.go.
  <!-- yap:ui -->
  ```diff
  @@ -10,3 +10,3 @@
  -old line
  +new line
  ```
  <!-- /yap:ui -->
  <!-- /yap:tool -->
<

  Header          The call as JSON. Short headers are single-line; longer
                  ones are pretty-printed between `<!-- yap:tool` and `-->`
                  and fold closed by default.

  Result text     What the model received. edit/write tools return short
                  confirmations; read-like tools return (truncated) content.
                  The header normally lands BEFORE the tool runs, so its
                  arguments are visible during execution. Live bash output is
                  followed via live(), never written into the buffer.

  <!-- yap:ui   Optional display-only diff for edits and writes, fenced as
                  ```diff between paired one-line markers. It is pure
                  decoration — editing or deleting it changes nothing.

The region is flattened into assistant transcript text (tool name, JSON
arguments, result) when the buffer is sent. Editing or deleting the visible
markdown changes the transcript directly; a region outside an assistant
message is skipped.

Tool results from content-bearing tools (read, bash, fetch, search, glob)
are wrapped in a fenced code block — read with a language info
string detected from the path, fetch as ```markdown, the rest plain.
write/edit return short confirmations and stay bare.

7. SESSIONS                                                  *yap-sessions*

A session is the conversation markdown file plus sidecar data: a file-backed
`notes.md` scratch buffer, an append-only audit log and an `assets/` folder holding
photos the conversation references, the backend's transient tool files, and
the agent's throwaway scripts, fetched downloads and generated artifacts.

`:Yap` sessions live in their own directory under
~/.config/yap/sessions/<cwd-slug>/: auto-named sessions and subagent children
group by month (<yy-mm>/<dd>-<sequence>/), and named forks live at
<cwd-slug>/<name>/. Older timestamp-named sessions (<yy-mm>/<dd-hh.mm.ss>/)
remain in place and open normally. Each has session.md (the conversation), notes.md (the
scratch buffer), audit.jsonl (the audit log) and assets/ (photos, fetched downloads
and working files).
Yap creates notes.md with the session, even if you never open the scratch buffer.

Every session records a `data_dir` in its frontmatter: the directory holding
its audit.jsonl, notes.md and assets/. For a transcript under the sessions
root it is the transcript's own directory; for one anywhere else (a project folder,
~/.yap, /tmp) it is a central directory under ~/.config/yap/sessions/, so the
transcript itself is the only file placed in the project. Because the tie is
recorded, a transcript can be moved out of its directory and still find its
audit log and assets. Yap recognises and adopts a yap-shaped markdown file
(yap frontmatter or a `# @system` heading) anywhere it is opened, while
ordinary markdown is left alone.
Sessions are saved after every turn and when the buffer stops being displayed
in any window; the file is created when the buffer opens. A native |:w| is
routed to that same save path (BufWriteCmd), so 'modified', |:w| and the exit
prompt behave normally.

Opening a session file directly — plain |:edit| or `nvim <file>.md` — adopts
it as a managed session (listed, keymapped, live tool tail attached), the same
as sessions() resume. A portable transcript counts as an ordinary open
session everywhere: it appears in the sessions() picker and in other
sessions' winbar rollup. The cwd picker also lists any session whose buffer is
open, including one opened directly from another project's folder — so
browsing ~/.config/yap/sessions/ and opening a transcript makes it show up in
sessions() for as long as it stays open. To browse every saved session across
all projects without opening files, use sessions("all") (`g+`). A next-to-file
or custom-path transcript is only listed while it is open — its location is
otherwise undiscoverable, so reopening it means opening the file.

The saved-session picker includes an ordinary blank session while its buffer
is loaded. Once unloaded, it is hidden unless it has a prompt, completed turn,
description or renamed transcript. An empty `:YapEval` is hidden even while
loaded; typing a question or completing a turn makes it visible.

Ordinary sessions are listed buffers backed by writable markdown files.
Rename `session.md` to set a title without losing normal file operations.
Deleting a session buffer uses Neovim's ordinary replacement
buffer behavior, without preferring waiting or running sessions.

                                                    *harness.sessions()*
require("harness").sessions(scope) is the session picker. `"cwd"` (the
default) lists saved sessions for the current project; `"all"` lists every
saved session across all projects under the sessions root, suffixing each root
row with its project so sessions from different worktrees are distinguishable.
Both scopes annotate open rows with a live status icon and nest forks (always)
and subagents (only while their parent is open) under their parent, drawn as a
box-drawing tree with a fork/agent glyph per row. Subagents (`b:yap_agent`)
remain unlisted and excluded from the winbar overview.

File operations are the session operations:

  rename the transcript   Rename `session.md` to set the session title. It
                         remains an ordinary writable markdown file.
  |:YapFork|              Copy the conversation into a new session directory.
  delete a region + send  Branch the conversation within the active session.

SCRATCH BUFFER

<leader>j toggles the scratch buffer, an ordinary file-backed Markdown buffer at
`<data_dir>/notes.md`, with spell checking in its window. It starts unlisted;
`:setlocal buflisted` in the scratch buffer adds it to |:ls|, and
`:setlocal nobuflisted` removes it. The choice persists while the buffer is
loaded, including across scratch buffer toggles. Leaving the session does not close
the scratch buffer, live tail or guard board. Close them with their toggles or ordinary
Neovim window commands.
Yap creates the file with the session and private permissions. Opening the
scratch buffer loads it. Native |:write| saves unsent drafts; Neovim's modified-buffer
and exit behavior applies. Consuming a section writes the whole scratch buffer
immediately, so a restart cannot resend the draft. A reopened session loads
its saved scratch buffer; within an editor instance the live buffer (including unsaved
edits) is reused. The scratch buffer is not a transcript and is excluded from session
discovery. Its two sections fold independently and carry an inline, display-only
state label preceded by a `·` so it reads as an annotation rather than buffer
text. A section handed to a turn also shows its icon in the winbar:

  uncommitted   The body is typed but not handed to a turn yet.
  pending       (steer) Submitted to the running turn.
  scheduled     (queue) Authorized to send when that turn ends.

An empty section shows no label.

Only these two headings delimit sections; other `# @...` lines are
ordinary scratch content, including when pasted inside a queue or steer.
When sent, role headings and yap marker lines are Markdown-escaped in the
session transcript so they cannot split the message. Each queue or steer
body is one message, and clearing a sent section leaves a blank line
beneath its heading.

  # @steer    While running, <C-s> submits a replaceable pending message
              for the next model boundary. Press <C-s> again to retract it
              without deleting the draft. Once delivered, it is cleared.
              If the turn ends first (a <C-c> stop included) it stays as a
              draft; pressing <C-s> here while idle sends it as the next
              message, even when queue has text. Editing the steer after
              submitting cancels it, so the sent text is always the text
              <C-s> saw: press <C-s> again to submit the revision.
  # @queue    While idle, <C-s> sends the whole body as one message. While
              running, <C-s> schedules one follow-up; press it again to
              unschedule without deleting the draft. The body is sent when
              that turn ends successfully. Editing the queue after
              scheduling cancels the follow-up, so the sent text is always
              the text <C-s> saw: press <C-s> again to schedule the revision.
              It never auto-sends merely because text was typed, or after a
              stop, failure, or session close.

<C-s> toggles a pending steer or scheduled queue while the turn runs; while
idle it sends the section under the cursor. Outside a section it only displays
a hint; move to steer or queue to send.
There is no selection-specific send. <C-Enter> in normal or insert mode picks a
template and inserts it at the cursor without sending it. The scratch buffer
is intentionally ephemeral — no file backs it, and it is dropped when Neovim
exits — but closing the session with |:bdelete| does not discard it: the
draft survives, comes back with the session, and its |<C-s>| still dispatches
to that session. |:write| {path} persists a draft explicitly.

AUDIT LOG                                                        *yap-audit*

audit.jsonl in the session's data directory (recorded as the frontmatter
`data_dir`: the transcript's own directory for `:Yap` sessions, or the
central directory for a transcript elsewhere) is
an append-only, JSON Lines record that survives restarts: every tool call
(full arguments), full tool results, image attachments, approval requests and
their Run/Deny answers, a retry line for each transient generation error, an
`error` line for a failed send (classified code + message), one `usage` line
per model step, and one `turn_end`
line per send regardless of outcome — model, prompt, completion,
`context_prompt` (the full last-step prompt size, including cached input),
optional cumulative `cache_read`/`cache_write` (present after nonzero cache
usage), cost, ms, and a `status` of `ok`, `error`, or
`cancelled`. Each generated session

description is also recorded as a `summary` line (`kind` `user` or `answer`
plus the `description`), so the history of auto-generated titles survives even
though the frontmatter keeps only the current label.

A `usage` line is one model step of one turn: `step` (1-based), the cumulative
`prompt`/`completion`/`cache_read`/`cache_write` the winbar chips read, and the
per-step `step_prompt`/`step_completion`/`step_cache_read`/`step_cache_write`.
The per-step split is what distinguishes reuse from re-billing. Step 1 of a turn
can only reuse the previous turn's history; every later step of the same turn
reuses what that turn already sent. So `step_cache_read` low on step 1 and high
on the rest means the turn's own output caches well but the previous turn's
output was re-sent fresh. See |yap-prompt-cache|.

The live tool tail (live()) is a separate, plain buffer that follows the
running tool's output — a `$ command` header per bash call plus its streamed
bytes. `Y` copies the command associated with the cursor line (header or
output) to the unnamed (`"`) and clipboard (`+`) registers. It is never
rebuilt from the audit log; the full streamed output lives in the tool's temp
log, and the audit log carries the tail-truncated result. A tail lives only
as long as its session: wiping the session buffer wipes the tail with it.
guard() lists every open session's parked approvals and the settled decision
history recorded since this Neovim started, and jumps to the matching tool
region in the session. |:YapClear| placeholders point back at the exact
audit-log lines they replaced.

The session directory is kept mode 0700 and its files mode 0600 — transcripts
and tool output routinely contain secrets.

PROMPT CACHE                                            *yap-prompt-cache*

Providers reuse a request only where it matches an earlier one from the first
token, so anything that reshapes already-sent history re-bills it. Inside a
turn the agent loop sends native items (tool calls, tool results, reasoning)
and extends them per step, which caches well. Across turns the markdown used to
be re-flattened into assistant text — the previous turn's tool round and
reasoning re-sent as new input.

The serve process now keeps that native array in memory and extends it, because
one `yap serve` process serves every turn of a buffer. Two exact checks gate a
replay: the flattened input must still start with what the previous turn sent,
and the transcript must still show exactly the bytes that turn wrote. Anything
else — an edit anywhere in the history, |:YapClear|, |:YapCompact|, a fork, a
model switch, or a restart — falls back to flattening the markdown, which is
exactly the behaviour without the cache. A restart therefore costs one cold
turn, not correctness.

To see it working, read the per-step `usage` lines: `step_cache_read` low on
step 1 and high on later steps is the signature described above.

8. FOLDING & NAVIGATION                                        *yap-folding*

`# @role` headings are folds; a closed fold shows the role and the first
content line. A whole yap:tool region folds to one `▸ tool: <name>` line;
thinking and error comment regions fold likewise. The YAML frontmatter folds
to a single `▸ options` line.

Three views, bound to <leader>1..3:

  <leader>1   only user prompts stay open
  <leader>2   conversation open, tool calls and thinking folded (default)
  <leader>3   everything unfolded

The system prompt and the frontmatter stay folded in views 1 and 2 and open
with everything else in view 3 (or earlier with za). Each window owns its
selected view and open/closed choices; a view keypress resets this window's
choices only.

<Tab> toggles the region under the cursor. ]t/[t, ]c/[c and ]e/[e jump to and
open a region without closing earlier ones. Clicking a closed fold opens it
(the same choice as <Tab>); native za/zo/zc, zA/zO/zC and zR/zM/zr/zm share
the same state. ]m/]u/]a only navigate. Message navigation and the message
text objects follow the same structural parse as folding, so a `# @user` line
inside a fenced tool result is literal content, never a message boundary.

9. WINBAR                                                      *yap-winbar*

The winbar is the session dashboard. On the left sits the buffer's state icon:
idle, awaiting your reply, stopped, error, or done for a finished subagent.
While a turn streams, an animated beacon replaces it: a fixed circle for
half a second, then a random circle face every 180 ms, slowing to 420 ms once
a tool has run 2s. When the turn ends the beacon gives way to the awaiting
icon. When the window is inactive the beacon and the title disappear; the
state icon stays.

Once a tool has run for 2s its name and elapsed time join the beacon
(`bash 12s`); a queued `# @queue` follow-up, a queued :YapClear, and a pending
`# @steer` add a tray icon, a broom icon and a steer icon immediately left of
that beacon. Fold views remain
available through <leader>1..3, but do not occupy the winbar. A rollup island
totals ALL OTHER yap sessions by state (streaming, awaiting you, stopped,
errored, idle). After the island: the
session title (a renamed transcript's filename, else the generated
description), truncated to 40 display columns. A provider/model island sits
centered in the bar. Right: two usage chips and a context-fill meter.

Reading the numbers                                    *yap-winbar-numbers*

  󰅐 N        Since-open: total tokens (prompt + completion) and cost for this
             buffer, accumulated since it was opened in this Neovim. Resets on
             reopen.
  󰆼 N        All-time: total tokens and cost for the whole session file,
             summed from every `turn_end` journal entry (|yap-audit|).
             Survives restarts; answers "what has this session cost".
  █▍░░░      Context fill: the last turn's full prompt as a bar of the
             model's context window. No label and no percentage sit beside
             it; the exact size belongs in usage details. Green below 70%,
             amber 70–90%, red 90%+.
  󰃨 82%      Cache read-hit rate = cache_read / (prompt + cache_read + cache_write),
             turn-wide. Green at >=70%, amber 40–70%, red below. Cache writes
             count as input, not hits. Shown only when cache usage is reported;
             a hidden chip does not prove 0% because some providers omit cache data.

Suffixes: `k` = thousands, `m` = millions. Costs are USD, computed from the
committed catalog (`agent/price/pricing.json`). On a freshly opened session
the two chips are equal; after a reopen they diverge.

The bar is width-aware and gives parts up in this order: cost detail, token
counts (prices stay), cache read-hit chip, context meter, then the centered
model island. The context meter outlives the cache chip. The model name is
this session's identity, so it outlives the right-side metrics; only a very
narrow bar drops it. The title then shortens. In inactive windows, the
centered session label drops when it no longer fits.

For a global segment independent of yap buffers, use
`%!v:lua.require('harness').overview()` in a statusline or tabline.

10. TEMPLATES & SKILLS                                      *yap-templates*

A template or skill is just a markdown file — the filename (minus `.md`) is
the name, the body is what gets inserted. They live in:

  ~/.config/yap/templates/     generic text (insert())
  ~/.config/yap/skills/        system-prompt material (insert())

Both configurable via `templates_dir` / `skills_dir`. Create the directory,
drop a file in, then insert(name) to insert it. `<C-Enter>` opens the picker,
which lists templates only; merge a skill with insert(name). In scratch,
`<C-Enter>` inserts a template's raw file at the cursor instead of sending it.

HOW TO WRITE A TEMPLATE                                      *yap-template*

A template is generic text you want injected as a message:

  - A leading `# @role` heading (`# @user`, `# @assistant`, ...) sets the
    role and is used as-is (a `# @user` heading reuses the existing trailing
    prompt instead of adding a second one).
  - Otherwise the body is wrapped in `# @user` and appended at the end.

A prompt you reach for often, as a template: >

  Review the current diff for bugs and code quality. Report:

  1. Correctness issues, most severe first.
  2. Edge cases that are not handled.
  3. A simpler alternative if one is obvious.

  Be concise; reference file:line for each finding.
<
A plain template is sent immediately after insertion. To prefill an assistant
reply instead, start the file with `# @assistant`.

A template containing LSP snippet syntax is expanded as a native Neovim
snippet: `$1`/`${1:placeholder}` become tabstops, `<Tab>`/`<S-Tab>` jump
between them. Snippet templates are not sent automatically.

HOW TO WRITE A SKILL                                          *yap-skill*

A skill is instructions for the system prompt, not the message history. Its
body merges into the `# @system` message. Optional YAML frontmatter
contributes one `description:` line to the `## Skills` list in the About Yap
prefix (refreshed on every send) and is stripped before merging: >

  ---
  description: Review frontend code for accessibility and semantics
  ---

  ## Frontend review

  When reviewing frontend code, check in this order:
  - accessibility: landmarks, labels, focus order, contrast
  - semantics: elements over styled divs; no nested interactive
  - type safety: no any, no @ts-ignore, no casts that hide errors

  Report findings as a list, most severe first, each with file:line and a
  one-line fix.
<
Everything after the second `---` is the body. Omitting the frontmatter is
fine. Do not include a `# @user` (or `# @assistant`) heading in a skill — it
would start a new message and split the instructions.

WHAT INSERT DOES

  insert(template)        wrap in `# @user` and append at the end, then send
                            (unless a snippet; a leading `# @role` heading
                            sets the role and is never duplicated)
  insert(skill)           merge the body into `# @system` (and reveal it)
  require('harness').insert(name, { at_cursor = true })
                            raw file above the cursor, no role logic

Plain templates send immediately; snippets, skills and raw at-cursor inserts
do not. While a send is in flight a template or skill steers instead: its body
(a leading `# @role` heading stripped) is injected at the running turn's next
tool boundary as a `# @user` message, exactly like a <C-s> steer
(|yap-sessions|). Raw insertion at the cursor is refused mid-turn.
The `## Skills` section of the About Yap prefix lists names + descriptions,
refreshed on every send.

11. THE GUARD GATE                                        *yap-guard-gate*

Every tool call passes a pre-execution approval gate made of static rules.
Each rule is declared in the tool's own source file, next to the tool it
guards (see tools.Gate and safety.Rule in the agent source), and is compiled
into the binary. `yap guard` prints the complete current list as JSON. When
a rule matches, the turn pauses for a Run/Deny confirmation; otherwise the
call runs.

bash is the one tool whose rules read the command line structurally: the
command is parsed (mvdan.cc/sh, the shfmt parser) and a rule matches on the
command word, its arguments, its pipeline and its command substitutions, not
on the raw text. Wrappers are stripped, so `sudo -n ssh host`, `timeout 20 ssh
host` and `cd /tmp && ssh host` are each one ssh, while `git commit -m "… ssh
…"` and `rg -n 'crontab -e' docs/` are arguments — never commands. A command
that does not parse trips no shell rule (bash would not run it either).

The set today:

  bash          what the sandbox cannot see. A raw network tool opening a
                listener or running a command (`nc -l`, `socat … EXEC:`);
                remote content executed by the shell that receives it
                (`curl … | sh`, `$(curl …)`); reaching another host (`ssh`,
                `scp`, `rsync host:`, `nc`); side effects on a remote
                (`git push`, a registry publish/push, a `gh` merge or
                release); local destruction the sandbox permits (`git reset
                --hard`, `git clean -f`); data leaving the machine (`curl`
                with a local-file flag, an `env`/`printenv` dump); machine
                state and privilege (`shutdown`, `systemctl reboot`, `sudo`);
                fork bombs; and secret-reveal commands — decrypting
                (age/gpg/sops/openssl), generating or exporting a private
                key, and reading a file under a secret directory.
  read/write    a path that is, or resolves into, a secret directory
  /edit/search  (~/.ssh, ~/.gnupg, ~/.aws, ~/.config/sops, /etc/ssh,
                /run/agenix, /etc/agenix) — approvable, never silently
                read or written.
  write/edit    a target outside the writable allowlist (the live |:pwd|,
                the session assets dir, `sandbox.allow_write`, and the temp
                dir) — pauses *before execution* with "write target outside
                allowed write paths (pre-run)" or the corresponding edit
                reason. `read` is deliberately NOT bounded — reading is not
                a write.

Secret paths and secret-reveal commands are one system (agent/safety/secrets.go):
adding a location to its list drives both surfaces, and scrub.go redacts any
secret that still reaches a result as the backstop.

The list deliberately does NOT restate the sandbox. A write outside the
writable allowlist — `rm -rf /`, a redirect onto /etc, `chmod -R`, `dd` onto a
device — is refused by the kernel and escalates through the same Run/Deny
(|yap-sandbox|), so a rule for it would be a second prompt for one decision,
and it would hide the fact that egress, remote side effects and privilege are
the things nothing else covers. Rules also stay away from ordinary work
(`git commit`, in-project `rm -rf`, `npm run build`, `nix build`): a prompt
that fires on routine commands teaches you to approve without reading.

A matching rule supplies the reason shown in the approval notification, the
audit log and the guard board. The gate is a steerable safety net, not a
security boundary on its own: a rule cannot see a command whose name is
computed (`eval "$CMD"`, `xargs`, `bash -c "$VAR"` — the runner itself is what
a rule can flag), and the path rules match text. The hard boundary is the
bubblewrap sandbox below (|yap-sandbox|), which the kernel enforces. Adding a
rule is a one-file change in the tool's source (recompile to pick it up);
nothing else needs editing — the rule then appears in `yap guard`
automatically.

THE SANDBOX                                                     *yap-sandbox*

bash runs inside a bubblewrap (bwrap) sandbox on Linux. The whole
filesystem is bind-mounted read-only, a small allowlist of directories is
re-mounted writable, `/tmp` is a private tmpfs, and the secret directories are
shadowed with empty mounts so the sandboxed process cannot read them. The
writable allowlist is the live |:pwd| (so it follows |:cd|), the session's
assets dir, and any `allow_write` entries from the `sandbox` config block.
The same allowlist also bounds the `write` and `edit` tools (see above), so
every mutating path — bash, write, edit — shares one definition of "where the
agent may write".

When a command's output contains "Read-only file system", the turn pauses
with "bash hit read-only filesystem; rerun unsandboxed". This is the single
path for every blocked write — the guard has no rule for one, since the
barrier already caught it — but it does not identify the failed path:
approving re-runs the entire command unsandboxed, while denying returns the
read-only failure to the model. A command that already
matched a static guard rule (e.g. `sudo`, `git push`) was approved
before it ran, so it runs unsandboxed
outright — the approval is the blessing to run it unconfined, and it never
prompts twice for the same command.

This is a write and read barrier, not a network or confidentiality boundary:
the sandbox does not unshare the network namespace, so a command can still
reach the internet, and the read-only view still shows everything not on the
denied-read list. It is on by default (disable with `sandbox.enabled = false`)
and silently falls back to running bash unsandboxed when bwrap is
absent or the platform is not Linux.

Scope: this sandbox bounds the *tools*, not the session. `bash` writes are
confined, but the backend, the editor and the other tools still run with the
full rights of the user account. To contain a whole session — untrusted
content, investigations — the flake ships `programs.yap.jail`, a launcher that
runs the editor under bubblewrap with only the launch directory and yap's own
config mounted (so nothing else of the home directory is reachable); see the
"Session jail" section of the README. The two compose: the per-tool
sandbox still applies inside the jail.

The guard board is bound to this Neovim process: it lists every open
session's parked approvals and the settled decision history (granted/denied/
timed-out) recorded since Neovim started. Parked approvals are live state,
answered via Run/Deny. Once answered, the outcome is recorded in memory as
settled history — the board never reads the audit log back, so it is empty on
startup and only shows what happened while this Neovim was open. `c` in the
guard board clears that in-memory history; the audit log is left intact.
Parked approvals are not touched by `c`. `Y` copies the bash command on the
cursor row to the unnamed (`"`) and clipboard (`+`) registers, including when
the row is folded.

12. TOOLS                                                      *yap-tools*

The agent ships a fixed set of compiled-in tools. `yap guard` lists the
approval rules that sit in front of them (|yap-guard-gate|).

  bash           Run a shell command. Sandboxed on Linux (|yap-sandbox|).
  read           Read a text file, 2000 lines / 50KB at a time.
  write          Write a whole file.
  edit           Exact-text replacements, several per call.
  search         Ripgrep search; returns path:line:content.
  glob           List files by pattern through ripgrep.
  fetch          Fetch a URL and return the readable content as markdown.
  subagent       Run a saved agent definition in a child session.
  sessions       List, search, and read other saved sessions (see |yap-sessions|).
  models         List provider/model combos and their prices.
  close_session  Close the session buffer once the turn has finished.

Configured MCP servers (see the `mcp` block in |yap-configuration|) add their
tools at runtime, named `mcp_<server>_<tool>`; they are discovered each turn
and are not part of this compiled-in list.

Independent read-only calls in one round run concurrently, up to four.

A subagent is a separate session: it gets its own context, may run a different
model, and returns only its answer to the parent. The calling model chooses
its permitted tool names per call, including runtime-discovered MCP tools;
agent definitions provide the system prompt and optional model, not tool
permissions. The normal approval guard and sandbox still apply. Definitions live in
`agents_dir` (|yap-configuration|), one markdown file per agent. An agent
session is internal to the conversation that spawned it: the single sessions()
picker nests it under its parent while the parent is open, and the tool result
carries a link to the session file, so a finished agent stays reachable. The parent waits up to 30 minutes; if
the child times out or is cancelled, the result still carries the child
session path so its work stays recoverable.

While a child runs, its activity is surfaced to the parent: the winbar shows
the current phase (running a tool, answering, awaiting approval) and the
parent's live tail mirrors the child's streamed output. The 30-minute wait
stops early if the child makes no progress for 3 minutes; a child parked on a
human approval does not count as idle. Only the final answer reaches the
parent's context — progress is UI and liveness, never re-sent to the model.

13. LANGUAGE SERVER                                            *yap-lsp*

A managed session buffer carries one language server, `yap lsp`, started and
attached by the harness. It provides four language features over standard
LSP, backed by the Go document parser (agent/document):

  Document symbols  An outline of the conversation: one symbol per message
                    (newest first), then the frontmatter block at the bottom
                    with each key as its own entry. Subagent tool calls nest
                    under the message that invoked them as children named
                    "agent · task". Other tool calls, thinking and machine
                    regions are not symbols; empty messages are dropped, and a
                    turn that only ran tools and then failed names itself by
                    its error.
  Completion        Frontmatter keys and values (`provider`, `model`,
                    `agent`, `tools`, ...), role headings, and `@path` file
                    references.
  Diagnostics       Structural warnings: unterminated or duplicate frontmatter,
                    invalid `turns`, unknown message roles, malformed tool
                    headers, and unclosed regions.
  Code actions      Quick fixes for an unterminated frontmatter block or an
                    unclosed tool region with a complete header.

The server attaches to session buffers for symbols, diagnostics and
completion. The scratch buffer gets `@path` and `# @steer`/`# @queue` completion,
without transcript diagnostics or symbols. Ordinary Markdown is left alone.
The `symbols()` picker (and its `<leader>s` keymap) presents the outline in the
server's order. Generic `document_symbol` pickers (e.g. mini.extra) re-sort by
line number and would put the frontmatter back on top, so yap ships its own.
Model completion reads the cached `yap models` list; it never hits the network, and opening a session never
starts an MCP server. Diagnostics are debounced and incomplete-tail warnings
are suppressed while a reply is streaming.

The built-in `vim.lsp.completion` is enabled on Yap buffers by default. Set
`require("harness").setup({ builtin_completion = false })` when using an
external completion engine so two popup menus do not compete. If you use
nvim-cmp or blink.cmp, their ordinary LSP source can already consume Yap's
completion items. An opt-in dedicated source is also available when you want
Yap completion without relying on the engine's generic LSP source:

>lua
  -- nvim-cmp: register once, then add { name = "yap" } to your sources
  local cmp = require("cmp")
  cmp.register_source("yap", require("harness.client.complete").cmp())

  -- blink.cmp: keep generic LSP elsewhere; use only Yap in sessions
  sources = {
    default = function(ctx)
      local base = { "path", "snippets", "buffer" }
      table.insert(base, 1, vim.b[ctx.bufnr].yap and "yap" or "lsp")
      return base
    end,
    providers = { yap = { module = "harness.client.complete", name = "Yap" } },
  }
<

Choose either the generic LSP source or the dedicated Yap source for session
buffers, not both, to avoid duplicate items. The source is active only at
frontmatter, role headings and `@path` references; it delegates item lookup
to `yap lsp`. Neither completion engine is a Yap dependency.

The language server is optional: if the binary is unavailable (or predates
`yap lsp`), editing is unaffected and the features simply stay off. Folding,
text objects and navigation remain local and synchronous; the server does not
participate in them. See R-language-intelligence in CONTRIBUTING.md for the
Lua/Go ownership boundary.

14. GLOSSARY                                                *yap-glossary*

The canonical vocabulary for yap's features and mechanisms. Use these names in
code, docs, and conversation; the right-hand column names the terms each
replaces.

  session             One conversation: its Markdown file, audit log, and
                      scratch queue. The artifact you open, name, fork, and
                      resume. (Not "chat", not "conversation".)
  session buffer      The Neovim buffer editing a session. (Not "chat
                      buffer".)
  transcript          The message text that is (re-)sent each turn — the
                      buffer's content with tool regions flattened into
                      assistant text. Distinct from the raw buffer, which also
                      holds frontmatter and marker regions.
  message             A `# @role` heading plus its body. (Not "block".)
  heading             A `# @role` line (`# @system` / `# @user` /
                      `# @assistant`).
  role                The `system` / `user` / `assistant` tag on a message.
                      Reserved for messages only.
  marker              A `<!-- yap:… -->` delimiter line. (Not "tag", "label".)
  region              A marker-delimited span — tool, thinking, error, or ui.
                      (Not "block", "detail".)
  tool region         One tool call + its result (header, result text,
                      optional yap:ui section). (Not "tool block".)
  send                The action (send(), `<C-s>`) and the in-flight
                      request it starts.
  turn                One completed send: one assistant reply, closed by a
                      `turn_end` journal line.
  reply               The `# @assistant` message a turn produces.
  prefill             Hand-writing an `# @assistant` message so the model
                      continues from it.
  steer               Mid-turn injection of a `# @steer` body at the next
                      model boundary. Distinct from prefill.
  scratch             The file-backed `notes.md` control buffer holding
                      `# @steer` / `# @queue`.
  audit log           The append-only `audit.jsonl` record of every tool
                      call, result, and turn. The durable record the buffer
                      doesn't carry.
  tail viewer         The live tool tail live() opens: one read-only
                      buffer per session following the running tool's output.
                      (Not "audit view", "live view", "audit drawer".)
  approval            The gate outcome that pauses a turn for a Run/Deny/
                      Inspect decision, triggered by a static guard rule.
                      (Not "blocked request".)
  guard rule          A static, deterministic condition declared in a tool's
                      source that pauses matching calls for approval (e.g.
                      bash's `sudo`). Listed in `yap guard`.
  agent definition    A `~/.config/yap/agents/<name>.md` file describing a subagent
                      (name, model, system prompt). (Not "role",
                      "subagent role".)
  subagent            A child session spawned by the `subagent` tool from an
                      agent definition.

"Block" survives only in standard Markdown/Vim senses unrelated to yap's
structure: code block, block-level, block comment, block device, block
element. "Blocked" as an ordinary verb (a blocked IP, a blocked read) also
remains. In yap's own structure, a foldable span is a region and a
role-delimited span is a message.
