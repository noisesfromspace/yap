==============================================================================
1. INTRODUCTION                                          *yap-introduction*

yap is an LLM chat plugin where the conversation lives in a plain editable
markdown buffer. A small Go binary (`yap`) is only a provider client: it
reads the message array on stdin and streams the reply to stdout. There is
no TUI, and no hidden conversation state anywhere.

The idea is stolen from gptel (Emacs): chat LLM APIs are stateless — every
request sends the full message array, so whoever holds the array holds the
truth, and that can be a text buffer. Consequences:

- Deleting a block removes it from the conversation: that is branching.
- Editing an assistant reply changes what the model "said".
- Writing your own `# @assistant` block steers the model (prefill).
- Yanking, undo, folds and rendering are just Neovim. `:undotree` is a
  free branch navigator.

2. COMMANDS                                                  *yap-commands*

                                                                    *:Yap*
:Yap                  Open a new chat buffer.

                                                                *:YapSend*
:YapSend              Send the whole buffer to the provider and stream the
                        reply into the buffer. Each send also injects
                        Neovim's current working directory into the request,
                        evaluated at send time. Thus `:cd` takes effect on
                        the next send and references such as "here" mean the
                        current Neovim directory. This request-only system
                        context is not written into the chat buffer.

                                                                *:YapStop*
:YapStop              Kill the in-flight request for the current buffer.

                                                                *:YapLive*
:YapLive              Open the session's tail buffer: one persistent
                        yap://<session>-tail buffer that renders the
                        session's audit log (|yap-audit|) as it streams
                        — a `$ command` header per bash call with its
                        drained output, one journal line per non-bash
                        tool call and result, and one journal line per
                        turn. Opens it in a split scrolled to the
                        bottom, or focuses the existing window. Never
                        opens by itself, but can be opened at any time
                        — even before a tool has run. The buffer is a
                        rendering, not a second log: it is rebuilt from
                        the audit log on reopen, so the live view
                        survives restarts.

                                                                *:YapClear*
:YapClear [keep]      Slim the context: replace the result bodies of
                        all but the last [keep] (default 2) yap:tool
                        regions with a one-line placeholder naming the
                        exact audit-log lines (path:line-range) where
                        the removed output lives. Headers
                        (the tool name + JSON arguments the model sees in
                        its history) and yap:ui
                        diffs stay; the full output is in the audit log
                        (|yap-audit|). Old tool output is the biggest
                        context consumer in long sessions and is usually
                        stale or re-fetchable — clearing it is the cheap
                        alternative to compacting the conversation.

                                                             *:YapCompact*
:YapCompact           Compaction as one command: insert the compact
                        prompt (a `compact` template in templates_dir,
                        or a built-in prompt), send the buffer, and —
                        once the summary has streamed in — offer to
                        delete the superseded history. The summary
                        stays a visible # @assistant turn; deletion is
                        an ordinary undoable buffer edit (see
                        |yap-compact|), never a hidden archive.

                                                                *:YapInsert*
:YapInsert [name]     Insert a template or skill into the buffer. A
                        template (see |yap-templates|) is wrapped in
                        `# @user` and appended at the end when it has
                        no leading heading; a leading `# @role`
                        heading (including `# @user`) is used as-is to
                        set the role and never duplicates the trailing
                        block. A skill merges its body into the
                        `# @system` block. With no argument, pick from
                        a combined list. This is the generic
                        text-injection mechanism: compaction is
                        inserting a summarize-prompt template, sending,
                        then deleting the old history.

                                                             *:YapInsertHere*
:YapInsertHere [name] Like |:YapInsert| but inserts the file's body
                        verbatim above the cursor — heading/role logic
                        aside, the raw primitive.

                                                        *:YapChangeModel*
:YapChangeModel {provider/model}
                        Change the provider/model combo for the current
                        buffer. Without an argument, pick a combo via
                        vim.ui.select. The picker is filled from
                        setup({ models = ... }) when configured,
                        otherwise by querying every provider in
                        config.json (GET /models) — no duplicate model
                        configuration needed. The query result is cached
                        for the session; |:YapReload| refreshes it.

                                                            *:YapSessions*
:YapSessions [all]    Pick a saved session to resume. Default scope is the
                        current project (cwd); "all" lists every project.
                        Sessions still on their auto-generated filename
                        (no description yet) are hidden; name one with
                        |:file| or let the first reply label it. Subagent
                        sessions are hidden too — reach a closed one via
                        its parent's frontmatter `subagents` list. Open
                        sessions stay listed by filename via
                        |:YapInstances|.

                                                            *:YapInstances*
:YapInstances         List every open yap session by its file path and
                        focus the picked one. Each line is annotated with
                        its state — `▶ running`, `✗ error`, `◉ waiting`
                        (a completed turn awaits your reply) or `○ idle` —
                        and needing-attention sessions sort first. Yap
                        buffers are unlisted — they never appear in |:ls|
                        or buffer pickers (MiniPick.buffers and friends),
                        and a session's tail buffer is never listed at all
                        (open it in the session with |:YapLive|). This is
                        how you move between sessions.

                                                            *:YapWaiting*
:YapWaiting           List only the open yap sessions awaiting a reply
                        (state `◉ waiting`) and focus the picked one — the
                        "needs you" subset of |:YapInstances|.

                                                               *:YapReload*
:YapReload            Reload the Lua modules (development).

3. KEYMAPS                                                    *yap-keymaps*

Set only in yap buffers, except <leader>r and <leader>w, which are global
(they list sessions across buffers, so they work from any file). Every
binding is a `keymaps` config key (see |yap-configuration|); the defaults
are shown below.

  <C-s> (n, i)          Send the buffer.
  <leader>c             Kill the in-flight request (see |:YapStop|).
  <leader>m             Change model (picker, see |:YapChangeModel|).
  <leader>l             Watch live tool output (see |:YapLive|).
  <leader>s             Toggle the session's scratch queue buffer: a
                        fixed-height, file-backed jotter below the chat.
                        `:w` saves it; an unsaved queue prompts on exit.
                        Inside the queue, <C-s> sends the whole buffer —
                        or the visual selection — to the chat and removes
                        it from the queue. When the agent is mid-turn,
                        <C-s> STEERS instead: the current line (or the
                        visual selection) is sent to the running turn and
                        injected at its next tool boundary as a `# @user`
                        block, without being removed from the jotter —
                        re-<C-s> to replace it, edit it until it lands.
  <C-t> (n, i)          Insert a template or skill (see |:YapInsert|).
  <leader>T             Insert a template or skill at the cursor
                        (see |:YapInsertHere|).
  <leader>r             List every open session with its status (see
                        |:YapInstances|).
  <leader>w             List just the sessions awaiting a reply (see
                        |:YapWaiting|).
  <Tab>                 Toggle one fold: open it persistently, or
                        close it again.
  ]m  [m                Next / previous message heading.
  ]u  [u                Next / previous user message.
  ]a  [a                Next / previous assistant message.
  ]t  [t                Next / previous tool call or thinking block
                        (opens the block it lands on).
  ]c  [c                Next / previous thinking block (opens it).
  ]e  [e                Next / previous error block (opens it).
  <leader>1             Fold all agent messages; user prompts stay open.
  <leader>2             Fold all tool calls and thinking blocks
                        (messages stay open).
  <leader>3             Unfold everything.

  Text objects (operator-pending and visual mode):
    im / am             inner / a message — the body without its `# @role`
                        heading, or the whole block including heading and
                        separator. `cim` replaces a message body while
                        keeping the role heading; `dam` drops a message.
    it / at             inner / a thinking, tool or error block — the
                        content without its markers, or the whole region
                        including markers. `dit` clears a block, `dat`
                        removes it entirely.

  View 1 is the default for opened session buffers; the system prompt
  stays folded in views 1 and 2. See |yap-folding|.

4. CONFIGURATION                                        *yap-configuration*

Lua setup: >lua

  require("harness").setup({
    bin = "yap",        -- path to the Go binary
    provider = "moonshot",
    model = "kimi-k3",
    models = {             -- optional: valid combos for the model picker
      "moonshot/kimi-k3",
      "deepseek/deepseek-v4-pro",
      "openai/gpt-5.6-sol",
    },
    system = "...",       -- fallback system prompt
    agents_file = vim.fn.expand("~/.config/yap/AGENTS.md"),
    roles_dir = "~/.yap/roles",   -- subagent role definitions
    sessions_dir = "~/.yap/sessions", -- autosaved sessions + scratch queues
    audit_dir = "~/.yap/audit",   -- audit logs
    notify_done = true,   -- vim.notify when a background turn finishes
    description_model = "openai/gpt-5-nano", -- smallest: on-send label
    description_answer_model = "openai/gpt-5-mini", -- bigger: final whole-session title
    syntax_highlight = true, -- keep markdown syntax colors (default)
    icons = { since = "󰅐", total = "󰆼", ctx = "󰊚" }, -- winbar chip glyphs ("" drops one)
    keymaps = { stop = "<M-Esc>" },  -- override any key; "" disables it
  })
<
`agents_file` is the system prompt for new buffers and is read per buffer,
so edits apply to the next chat. When missing or empty, `system` is used.
The path is used verbatim (no `~` expansion); the default is
`$XDG_CONFIG_HOME/yap/AGENTS.md` (or `~/.config/yap/AGENTS.md`).

`roles_dir`, `sessions_dir` and `audit_dir` locate yap's data under
`~/.yap/`. A leading `~` is resolved against the real home directory —
never the current working directory — and an absolute path is used
verbatim. This is deliberate: an unset, empty, or relative `$HOME` must
not make yap write its `.yap` folder into the project. The defaults are
`~/.yap/roles/`, `~/.yap/sessions/` and `~/.yap/audit/`.

The harness always prepends its own `# About Yap` boilerplate (buffer
semantics, marker rules) as the first system message of every turn. That
boilerplate is independent of `agents_file` and is never written into the
session file, so the `# @system` block stays clean.

`notify_done` (default true) fires `vim.notify` when a turn completes in a
buffer that is not the current one; the turn's `turn_end` payload (model,
tokens, cost, ms) is attached to the `User YapTurnDone` autocmd so other
plugins can hook the same event (noice/nf-notify rendering, chaining a
next send). Disable the toast with `notify_done = false`; hook the same
event with your own `User YapTurnDone` autocmd.

`syntax_highlight` (default true) keeps tree-sitter's markdown syntax
highlighting on chat buffers. Set it to false to drop syntax colors for a
little more headroom. Note that profiling attributed a per-scroll cost to
"treesitter" that was actually touchup re-rendering plus live-buffer churn:
the highlighter itself is incremental and effectively free, so the default
keeps colors on.

`icons` sets the leading glyph of each winbar usage chip (|yap-winbar|):
`since` (this buffer, since open), `total` (the whole session's audit
total), and `ctx` (context fill). Defaults are Nerd Font v3 glyphs; set
any to `""` to drop its glyph on fonts without it.

`relativenumber` is left alone: chat buffers keep whatever `'relativenumber'`
setting the user has. The slowness that looked like relativenumber was
mini.diff's number-column rendering colliding with it. yap sets the
buffer-local `minidiff_disable` flag (and detaches mini.diff if it already
attached) so diff hunks — meaningless on a transcript — don't re-render the
gutter on every redraw.

`keymaps` maps each action to its key sequence, so any of |yap-keymaps|
can be rebound from `setup()`. The table keys are: `send`, `stop`,
`change_model`, `live`, `scratch`, `insert`, `insert_here`, `sessions` (global),
`waiting` (global), `next_message`/`prev_message`, `next_user`/`prev_user`,
`next_assistant`/`prev_assistant`, `next_tool`/`prev_tool`,
`next_think`/`prev_think`, `next_error`/`prev_error`, `view_1`..`view_3`,
`toggle_fold`, `inner_message`, `around_message`, `inner_block`,
`around_block`. Buffer-local keys are applied whenever a session opens
(and on |:YapSessions| resume / adoption); `sessions` and `waiting` are
installed once by `setup()`. Set an entry to `""` to disable that binding.

The session description shown in the winbar (|yap-winbar|) and session
picker is generated in two stages, both sharing one `description:` key in
the buffer frontmatter. `description_model` (default `openai/gpt-5-nano`)
is the smallest model and labels the session from the latest user message
as soon as you send, so the winbar and picker have a title before the agent
answers. `description_answer_model` (default `openai/gpt-5-mini`) is a
bigger model that writes the final title once the turn completes (the
buffer is back on the `# @user` block): a short "Subject: change" phrase
centered on the overall goal, so the session reads as a findable reminder
later. Set either to "" to disable that stage; the description survives in
the buffer frontmatter either way.

`templates_dir` and `skills_dir` (defaults `~/.config/yap/templates/`
and `~/.config/yap/skills/`) hold the plain-markdown files inserted by
|:YapInsert|. `skills_intro` (default true) adds a `## Skills` list of
name + description to new chats' system block — discoverability only,
bodies are never auto-loaded. See |yap-templates|.

Templates & skills                                          *yap-templates*

The generic mechanism behind compaction, snippets and skills is one
command: insert a text file into the buffer. A template or a skill is
just a markdown file — the filename (minus `.md`) is the name shown in
the picker, and the body is what gets inserted. There is no separate
serializer and no frontmatter schema beyond the one optional
`description:` key described below.

Where they live: >

  ~/.config/yap/templates/     generic text (|:YapInsert|)
  ~/.config/yap/skills/        system-prompt material (|:YapInsert|)
<
Both are configurable (`templates_dir`, `skills_dir`). Create the
directory, drop a file in, then `<C-t>` (or `:YapInsert <name>`)
to insert it; `<leader>T` (`:YapInsertHere`) dumps the raw file at
the cursor.

HOW TO WRITE A TEMPLATE                                      *yap-template*

A template is generic text you want injected as a message. It behaves
by one rule: >

  - A leading `# @role` heading (`# @user`, `# @assistant`, ...) is
    used as-is to set the role. A `# @user` heading never duplicates
    the trailing block — it is reused via append_message.
  - Otherwise the body is wrapped in `# @user` and appended at the end.
<
A prompt you reach for often, as a template: >

  Review the current diff for bugs and code quality. Report:

  1. Correctness issues, most severe first.
  2. Edge cases that are not handled.
  3. A simpler alternative if one is obvious.

  Be concise; reference file:line for each finding.
<
The body is wrapped in `# @user` for you, so you can leave the heading
out. To prefill an assistant reply instead, start the file with
`# @assistant`. A leading `# @user` heading is fine too — it sets the
role and fills the trailing `# @user` block without duplicating it.

A template containing LSP snippet syntax is expanded as a native
Neovim snippet: `$1`/`${1:placeholder}` become tabstops the cursor
lands on after insertion, and `<Tab>`/`<S-Tab>` jump between them.
For example, a template body of: >

  Investigate: ${1:<topic or path>}
<
inserts with the cursor on `${1:<topic or path>}` (selected, so typing
replaces it) and `<Tab>` afterwards continues past the end of the
inserted block.

HOW TO WRITE A SKILL                                          *yap-skill*

A skill is instructions you want in the system prompt, not in the
message history. Its body merges into the `# @system` block, so a
skill inserted into a fresh chat becomes part of the standing
instructions for that conversation.

The optional YAML frontmatter contributes one `description:` line to
the `## Skills` intro list shown in new chats, and is stripped before
the body is merged: >

  ---
  description: Review frontend code for accessibility and semantics
  ---

  ## Frontend review

  When reviewing frontend code, check in this order:
  - accessibility: landmarks, labels, focus order, contrast
  - semantics: elements over styled divs; no nested interactive
  - type safety: no any, no @ts-ignore, no casts that hide errors

  Report findings as a list, most severe first, each with file:line
  and a one-line fix.
<
Everything after the second `---` is the body. The `---` lines and
`description:` never reach the model. Omitting the frontmatter is
fine — the skill then simply has no intro line.

A skill body merges into `# @system`, so do not include a `# @user`
(or `# @assistant`) heading in it — a role heading would start a new
message block and split the skill's instructions. The one exception
is an agent skill that intentionally documents the buffer's message
format and quotes the headings as examples.

WHAT INSERT DOES

  :YapInsert <template>   wrap-in-# @user and append at the end
                            (a leading `# @role` heading sets the role
                            and is never duplicated)
  :YapInsert <skill>      merge the body into the `# @system` block
  :YapInsertHere <name>   raw file above the cursor, no role logic

All three go through the normal append paths (R7 blank-line handling);
insertion never touches existing lines. While a send is in flight a
template steers instead: its body (a leading `# @role` heading is
stripped) is injected at the running turn's next tool boundary as a
`# @user` block, exactly like a <C-s> steer from the scratch queue
(see |yap-sessions|). Skills and `:YapInsertHere` are still refused
mid-turn — they edit the buffer, which a streaming turn must not be
disturbed. The `## Skills` intro in a new chat is discoverability
only — names and descriptions, never skill bodies (toggle it off with
`skills_intro = false`).

COMPACTION RECIPE                                           *yap-compact*

Compaction is the template mechanism applied to a long conversation —
the summary stays a visible, editable turn, never an invisible rewrite.
|:YapCompact| automates the three steps below (insert, send, then
offer to delete); the manual recipe remains available:

  1. `<C-t>` and pick `compact` (ships at
     `templates/compact.md`; copy it into your templates_dir), or
     write your own "summarize the conversation above…" prompt.
  2. `<C-s>` to send it.
  3. Delete the history above the summary (deletion = branching,
     |yap-introduction|). The summary block is the new context.
<
The archive-marker idea (folding old messages away) is deliberately
NOT part of this: the buffer is the truth, so old text is either in
context or gone — folding it away would be hidden state.

Config and runtime data:

  ~/.config/yap.json  Providers and optional pricing: >json

    {
      "providers": {
        "moonshot": { "base_url": "https://api.moonshot.ai/v1",
                      "api_key_env": "MOONSHOT_API_KEY" }
      },
      "decision": { "base_url": "https://openrouter.ai/api/alpha/decisions",
                    "api_key_env": "OPENROUTER_API_KEY",
                    "model": "typesafe/jev-1.13" },
      "pricing": { "kimi-k3": { "input": 0.60, "output": 2.50 } }
    }
<
                        Any OpenAI-compatible /chat/completions endpoint
                        works. API keys come from the named env vars.
                        `pricing` (USD per 1M tokens) overrides the
                        committed catalog for a model; most models are
                        priced automatically from the embedded catalog
                        (agent/pricing), so `pricing` is only needed for
                        models the catalog misses or for a provider whose
                        price differs from the catalog. `decision`
                        configures the decision-model backend behind the
                        jev tool (|yap-tools|); it defaults to Jev via
                        OpenRouter's Decisions API, OPENROUTER_API_KEY,
                        and the pinned `typesafe/jev-1.13` release.

  ~/.config/yap/AGENTS.md   Default system prompt (see above).
  ~/.yap/sessions/          Autosaved sessions and their scratch queues,
                            see |yap-sessions|. Override with `sessions_dir`.
  ~/.yap/audit/             Audit logs, see |yap-audit|. Override with
                            `audit_dir`.
  ~/.yap/roles/             Subagent role definitions. Override with
                            `roles_dir`.

Tools                                                        *yap-tools*

Tools are NOT configured anywhere — they are Go files in agent/tools/
package of the yap source tree, one file per tool, each
self-registering in init(). Only tool files live in agent/tools/;
shared helpers (path guarding, SSRF checks, secret scrubbing, safety
scanning, unified diffs) go in agent/utils/. Adding or changing a tool
= editing a file and recompiling (CGO_ENABLED=0). A tool returns a
result (sent to the model) and optionally a ui payload (display-only
yap:ui section,
see |yap-tool-block|). The binary runs the whole agent loop in one
process, bounded at 300 iterations per send. Built-ins: ls, read, fetch,
bash, python, curl, git, write, edit, search, glob, websearch, quickfix, ssh,
jev, close_session. The `subagent` tool delegates to a role defined in
`~/.yap/roles/<name>.md` (or the directory set by `roles_dir` in
`require('harness').setup()`). Roles use YAML frontmatter: `name`, `model`, optional
comma-separated `tools`; the body is its system prompt. It creates a normal
Yap session named `<parent-stem>-<six-hex>.md` in the same project directory.
The parent tool call waits for the child's turn to finish, then receives its
final answer and session path; open the child from the parent's frontmatter
`subagents` list or, while it is open, via |:YapInstances|. Bare Pi
role model names cannot identify a Yap provider, so they inherit the parent's
provider/model; use an explicit `provider/model` to override it. Pi tool names
`grep`, `find`, `webfetch` map to Yap's `search`, `glob`, `fetch`. Unsupported
role tools are reported before the child starts. A role without
`tools` gets a read-only set (ls, read, search, glob, fetch, git,
websearch, quickfix, jev); write/bash/python/curl/ssh must be requested
explicitly via `tools`. Role tool lists are enforced by the child
backend. The parent receives the
child's error text on failure. Delegation times out after ten minutes;
stopping the parent or timing out stops its running child, but retains its
Markdown file. Children are linked by the
filename prefix: renaming a parent does not rename its existing children.
There is no background spawn or child-to-child messaging.
search and glob shell out to
ripgrep (rg): search returns path:line:content matches, glob lists files
(gitignore-aware); both truncate to read's limits (2000 lines / 50KB).
websearch queries the Exa search API (api.exa.ai) and returns up to N
results as markdown; its API key is read from the env var named by
`websearch.api_key_env` in ~/.config/yap.json (default `EXA_API_KEY`).
jev asks a decision model (Jev via OpenRouter's Decisions API by
default) for typed, calibrated answers — P(yes) for noul questions, a
winner + confidence + probabilities for choice, a weighted position for
score — about a state the caller supplies. It is a decision primitive,
not a chat model, and returns probabilities rather than prose. The
backend is the agent/decision.Model interface, so other decision models
with the same typed surface can be swapped in; `decision.*` in
~/.config/yap.json sets base_url, api_key_env, and model.
curl shells out to the system curl binary: method, headers, user-agent,
body, redirects, timeout and extra curl flags are all settable, and it
sends a browser User-Agent by default to get past agent blocks (it is
fetch's versatile sibling for follow-up fetches; fetch extracts the
main content as Markdown, while curl returns the raw response body and
does not run JavaScript). Redirects are followed one hop at a time and
each hop's host is re-checked against the SSRF guard; flags that could
turn curl into a file-writer or an SSRF vector (--unix-socket,
--config/-K, output/-o/-O/--output-dir, --resolve, --connect-to,
--dump-header/-D, --trace*, --interface) are refused. Both `fetch` and
`curl` accept an optional
`safety` parameter: when true, the result is scanned with the decision
model (jev, see above) for prompt-injection content before it is
returned, and flagged content gets an advisory warning line prepended
naming the probability (the content is still shown and sent, only
marked). Each true call costs one extra decision-model round-trip, so
use it for untrusted sources rather than every fetch. git runs read-only subcommands
(status, diff, log, show, blame) in the project root with pager, color
and credential prompts disabled; output is head-truncated like search.

ssh runs non-interactive commands via the system OpenSSH client. A foreground
ControlMaster per user/host/port is owned by the Yap backend and its socket
lives in a private mode-0700 temporary directory. The socket grants local
processes that can access it the authority to run commands over the connection.
The backend closes masters and removes sockets on close=true, normal exit,
:YapStop, and SIGTERM; a hard crash can leave a stale private socket directory.
No ControlPersist or agent/X11 forwarding is enabled. Each command runs in a
new SSH session with a 120s default timeout; a nonzero exit is reported.
OpenSSH uses its default identities and local ssh-agent (including FIDO keys).
The tool disables ~/.ssh/config so aliases and proxy commands cannot bypass
its trust boundary, and requires the requested host in NixOS's
/etc/ssh/ssh_known_hosts. User known_hosts entries cannot authorize a host.
BatchMode disables interactive password/PIN prompts; agent-mediated FIDO touch
can still prompt through the local agent. Commands run unsandboxed over your
credentials, so a dangerous command (see R15) pauses the turn for a Run/Deny
confirmation. The master is shared across session
buffers while Neovim's backend is alive.

Tool parameters are declared as a Go struct per tool; the schema sent
to the provider is generated from it by reflection, and incoming
arguments are validated against the compiled schema before Run.

quickfix replaces the current Neovim quickfix list with a batch of source
locations. Each invocation creates a new list on the quickfix stack, so the
previous list remains reachable with |:colder| / |:cnewer| (subject to
|'chistory'|). The Neovim side applies the structured live tool_call event;
there is no parsing of assistant text. Historical tool blocks do not execute,
so reopening a saved session never replays the quickfix side effect.

close_session asks Neovim to close the session buffer once the current turn
has finished and the session file has been saved. It is a frontend side effect
like quickfix: the tool returns only a confirmation, and the Neovim side
marks the buffer from the live tool_call event and wipes it on turn
completion (the reply still streams, then the file is saved, then the buffer
is deleted). The session file is untouched, so the conversation remains
resumable via |:YapSessions|. Subagents do not get this tool, so a child
cannot close the parent session.

write creates or overwrites files (creating parent directories); edit
does exact-text replacement with pi's semantics: every edits[].oldText
is matched against the ORIGINAL file, must occur exactly once, and
must not overlap another edit; application is span-based so a newText
can never match inside another edit's oldText. Both return short
confirmations to the model (R12 result policy); when a file is
overwritten/edited, a unified diff (sergi/go-diff, in-process) is
attached as a display-only yap:ui section (|yap-tool-block|).

bash runs commands non-interactively (stdin is /dev/null) in their own
process group: on timeout (default 120s, model-adjustable) the whole
group is SIGKILLed, and :YapStop takes in-flight commands down with
the binary. Output streams into a temp file; the binary announces the
path on stderr (yap:event, see |yap-protocol|) and the Lua side
drains it into the session's tail buffer (:YapLive) — live output
never enters the chat buffer (R16). The result is
truncated to the LAST 2000 lines / 50KB with the full output kept in
the temp file; a non-zero exit is reported to the model, not treated
as an error. bash is unsandboxed, but a dangerous command (see R15)
pauses the turn for an explicit Run/Deny confirmation before it runs.

python runs a Python 3 script the same way, as a fresh process (no
state carries between calls — one self-contained script per call), with
the same process-group timeout, live tail, and 2000-line / 50KB tail
truncation. It takes exactly one of `code` (a small inline script,
written to a temp file and run as `python3 <file>`) or `file` (a path
to an existing script, resolved relative to the Neovim cwd like write's
path — write the file first with the write tool, then run it). `file`
is for larger scripts so the code lives in a real, editable file the
user can `gf` to; the header shows only the file reference. A failed
script returns its traceback to the model as text. Like bash, it is
unsandboxed, but dangerous source (subprocess/os.system/…, shutil.rmtree,
see R15) pauses the turn for an explicit Run/Deny confirmation.

Path fields on write, edit, read, ls, glob, search, git, and python
(file and cwd) — plus bash's cwd — expand a leading ~ or ~/ to the
home directory. Write larger generated scripts under ~/.yap/scratch/
(shared, outside any project repo) so they stay out of git.

write/edit tool headers in the buffer are SLIMMED (R12): the arguments
show `[N lines]` / `[N edits, +A/-B lines]` instead of the content —
the yap:ui diff below shows the change, the file on disk is the
ground truth, and the full arguments are in the audit log. Every tool
call and result is also emitted as a yap:event and persisted there,
see |yap-audit|.

5. BUFFER FORMAT                                                *yap-buffer*

A yap buffer is plain markdown. Headings delimit messages: >

  # @system
  # @user
  # @assistant

Everything between headings is message content. Everything before the first
heading is ignored by the parser — that is where the session's model state
lives, as YAML frontmatter:

  ---
  provider: moonshot
  model: kimi-k3
  created_at: 2025-09-29T19:22:33Z
  updated_at: 2025-09-29T19:24:01Z
  models:
    - moonshot/kimi-k3
    - deepseek/deepseek-v4-pro
  subagents:
    - /home/martijn/.yap/sessions/.../session-a1b2c3.md
  ---

`provider`/`model` is the combo to resume with; `models` is the ordered
history of every combo used in the session (most-recent-last); `subagents`
is the ordered list of subagent session paths the session ran
(most-recent-last); `created_at` records the session's creation and
`updated_at` its last write. The
frontmatter is the ONLY durable session state: yap writes the model fields
on :Yap and |:YapChangeModel|, stamps `updated_at` on every save, reads the
block on open, and sends never rewrite it mid-turn.
Token totals and cost are NOT stored here — the winbar accumulates
them per-buffer (|yap-winbar|), and the durable session total is
derived from the audit log's turn journals (|yap-audit|), not from
the file. Legacy session files without frontmatter simply keep the
setup() default combo.

A yap buffer never attaches a language server: the buffer is the
conversation (R1), and a markdown LSP's semantic-token/inlay-hint stream is
pure per-redraw cost on a large session. setup_buffer marks each buffer and
an LspAttach guard in setup() stops any markdown client from attaching.

The active combo comes from the frontmatter on open, then from per-buffer
vars set by |:YapChangeModel|, falling back to setup() defaults. The
buffer holds the model state (R1) but NOT token/cost totals: those
accumulate in memory for the lifetime of the buffer, and reopening a
session starts them from zero.

6. MARKERS                                                    *yap-markers*

HTML comment regions of the form `<!-- yap:<word>` ... `-->` are shown in
the buffer but NEVER sent to the provider as buffer text; the parser skips
them (one exception: yap:tool, which is FLATTENED into assistant transcript
text — see below).

  <!-- yap:thinking   Provider-exposed reasoning or reasoning summaries
                        streamed by GoAI. Folded away with the assistant
                        block and never included in persisted history.

  <!-- yap:error      Backend error record, left after a failed send.

  <!-- yap:usage      Token usage reported at end of stream. Consumed
                        immediately: folded into the winbar totals and
                        the line is removed.

Tool blocks                                                *yap-tool-block*

A tool call and its result are ONE region inside an assistant block: >

  <!-- yap:tool {"id":"call_1","name":"edit","arguments":{...}} -->
  Successfully replaced 1 block(s) in main.go.
  <!-- yap:ui -->
  ```diff
  @@ -10,3 +10,3 @@
  -old line
  +new line
  ```
  <!-- /yap:ui -->
  <!-- /yap:tool -->
<
  Header          The complete call as JSON. parse_buffer flattens it into
                  assistant transcript text (tool name + JSON arguments).
                  Two forms: single-line when short (≤ 120
                  chars, typical for bash/ls/read), otherwise
                  pretty-printed multi-line JSON between `<!-- yap:tool`
                  and `-->`: >

  <!-- yap:tool
  {
    "id": "write_0_a3317f99",
    "name": "write",
    "arguments": { "content": "...", "path": "/tmp/x.md" }
  }
  -->
<
                  Multi-line headers fold closed by default (a level-3
                  fold with `▸ tool: <name>` foldtext; za to inspect) —
                  the yap:ui diff below is the visual record, so the
                  arguments are never shown twice. Thinking and ui
                  regions fold the same way; single-line headers stay
                  unfolded.

  Result text     Exactly what the model received; in context. edit/write
                  tools return confirmations (pi/Codex pattern), read-like
                  tools return (truncated) content.

                  The header lands BEFORE the tool runs, so the call
                  (and its arguments) is visible while it executes;
                  the gap to the result honestly represents execution
                  time. Live output is followed via |:YapLive| (R16),
                  never written into the buffer.

  <!-- yap:ui   Optional display-only payload: a rendered unified diff
                  for edits and writes (creates included, as an all-`+`
                  diff), fenced as ```diff between paired one-line
                  markers. Block level — unlike thinking, not an HTML
                  comment — so treesitter parses the fence and injects
                  the diff parser for real +/-/@ highlighting. Parse-
                  excluded like thinking: editing or deleting it changes
                  nothing. Pure decoration.

parse_buffer flattens the region into ordinary assistant transcript text:
the tool name, its JSON arguments, and the result, all as visible text —
never native tool-call/tool-result messages. Editing or deleting the
visible markdown changes the transcript directly. Sanitizer: a region
outside an assistant block is skipped; a missing/empty result yields an
empty labelled result; a malformed header skips the region with a notification.

Marker regions close on a line that is exactly `-->`; content merely
containing it never closes early for OUR parser. Markdown renderers are
stricter: HTML comments are character-based, so ANY `-->` — even inline
in backticked prose — would close the comment early. The binary
therefore neutralizes every `-->` to `-- >` inside comment regions
(streamed thinking via a line-buffering escaper, since chunks split
mid-line; error text). A backslash can't do that job:
`\-->` still CONTAINS the `-->` a character-based scanner looks for.

Everywhere else the rule is one VISIBLE backslash-escape, valid
CommonMark for ASCII punctuation, applied once at write time: a
tool-result line starting with a yap marker opener becomes
`\<!-- yap:…`, and <style>/<script> open tags become `\<style` /
`\<script`. Renderers show the literal text, treesitter sees an escape
instead of a tag, and the line-start-anchored Lua parser never matches.
Invisible bytes were rejected: a zero-width space breaks
markdown_inline's html_tag grammar (the comment fails to parse and the
ZWSP renders as a literal <200b>), and a soft hyphen hides the
mutation from the user while still reaching registers and the model.

Tool RESULTS from content-bearing tools (read, bash, ls, fetch, curl,
git, search, glob) are wrapped in a fenced code block — read with a
language info string detected from the path extension, fetch as
```markdown, the rest as a plain fence.
The buffer is markdown, and raw file content or command output
gets parsed by markdown_inline (links, emphasis, headings, <hr>) and
picks up stray styling; the fence renders it as code instead and lets
treesitter inject the language. The fence is one backtick longer than
any run inside the result, so a ``` line in the content can't close
it early; the same fenced string goes to the model, so the buffer and
the replayed history stay identical across turns. write/edit return
short confirmations and stay bare. The unclosed-fence guard remains as
a fallback for those unfenced results.

Why the <style>/<script> escaping matters: fetch returns Markdown that
may embed raw HTML, and those open tags let treesitter's combined HTML
injection hand
their content to the css/javascript parsers, and those raw-text
injection ranges bleed to the end of the buffer — everything after the
result renders as css/js. The backslash-escaped open tag keeps the
document a fragment and the parse bounded.

7. SESSIONS                                                  *yap-sessions*

A session is just the buffer's markdown written to a file — the buffer IS
the serialization, there is no other format. Files live under
~/.yap/sessions/<cwd-slug>/ and are autosaved after every completed reply.
The file is created when the buffer is opened, so a fresh session is
file-backed from the start and can be named with |:file| before the first
reply; every autosave goes through |:write|, so the buffer owns its file:
'modified', |:w|, and the exit prompt all behave like any normal file buffer.
The audit log (<session>.jsonl) is written in the audit dir
(|yap-audit|) as the session runs and follows the session name across
|:file| renames. The scratch queue is the same kind of sibling:
~/.yap/sessions/<cwd-slug>/<session>.queue, a plain file-backed buffer
for queuing agent tasks. Unlike the autosaved session, the queue is
saved manually — `:w` in the jotter writes it, and an unsaved queue
triggers the normal modified-buffer prompt on exit. Pressing <C-s> in
the queue sends its contents (or the active visual selection) to the
chat as a `# @user` message and removes them from the queue. While the
agent is streaming, the same <C-s> steers instead: the current line (or
the visual selection) is handed to the running turn and injected at its
next tool boundary as a `# @user` block — the draft stays in the jotter
so you can keep shaping it (re-<C-s> to replace it), and a steer that
arrives after the turn ends is sent as a follow-up turn. Opening a session
file directly — plain |:edit| or
`nvim <file>.md` — is recognized: the buffer is adopted as a managed
session (unlisted, keymapped, tail attached), the same as |:YapSessions|
resume.

File operations are the session operations (pi equivalents, but manual):

  :file new-name.md     Name a session; the picker shows the chosen name.
  :saveas copy.md       Fork: the original file is untouched, the buffer
                        continues as the copy.
  delete a block + send Branch the conversation.

AUDIT LOG                                                        *yap-audit*

The session file holds the context; the audit log holds everything the
context doesn't carry. ~/.yap/audit/<cwd-slug>/<session>.jsonl,
append-only, survives restarts. It is JSON Lines: one JSON object per
line, timestamped by the Lua side as each |yap-protocol| event arrives:

  tool_call    {"type","id","name","args","ts"} — every tool before it
               runs, FULL arguments (bash included, so timeout/cwd
               survive); id matches the buffer's tool header and the
               tool_result below
  tool_start   {"type","name","log","command","ts"} — bash/python's temp log
               (`command` is scrubbed of obvious secrets)
  output       {"type","name","data","ts"} — streamed bash/python output chunks
               (synthesized by the Lua side as it drains the temp log)
  tool_result  {"type","id","name","bytes","result","ts"} — full result
  approval_request {"type","id","command","ts"} — a dangerous command paused
               the turn for a human Run/Deny
  approval_result  {"type","id","approved","ts"} — the human's answer
               (synthesized by the Lua side)
  approval_timeout {"type","id","ts"} — no answer; denied
  retry        {"type","attempt","delay_ms","error","ts"} — a transient
               generation error (429/5xx/network) was retried before the
               step emitted any output
  turn_end     {"type","model","prompt","completion","cost",?,
               "context_window",?,"ms","ts"} — one per completed send

The tail buffer (|:YapLive|) is the human-readable rendering of these
events and is rebuilt from the file on reopen. |:YapClear| placeholders
correlate a region's tool-call id with its tool_call..tool_result
line range, so a cleared body points back to exactly what it replaced.
This is what makes the slimmed write/edit headers (R12) and
|:YapClear| lossless: anything removed from the context exists here
verbatim, machine-readable.

The audit directory is created mode 0700 (the log holds full tool
arguments and results).

8. FOLDING & NAVIGATION                                        *yap-folding*

`# @role` headings are folds (foldexpr); a closed fold shows the role and
the first content line. Inside a message fold, level-3 folds collapse
display regions: a whole `yap:tool` region (header, result and ui
diff, both header forms) folds to one `▸ tool: <name>` line; thinking
and error comment regions fold likewise.

Three views, bound to <leader>1..3, each applied unconditionally so a
keypress always lands on the same state:

  <leader>1   only user prompts stay open
  <leader>2   conversation open, tool calls and thinking folded (default)
  <leader>3   everything unfolded

The system prompt is reference material: it stays folded in views 1 and
2 and opens with everything else in view 3 (or earlier with za).

The applied view shows in the winbar (`Ⓕ1`-`Ⓕ3`), see |yap-winbar|.
View 2 is applied once when a session buffer is opened. Fold levels are
role-dependent (user 1, assistant 2, tool/thinking/system 3), so the
three views are pure 'foldlevel' 1/2/3 with no manual foldclose: manual
closes combined with expr folds made Neovim re-evaluate every fold on
each edit — hundreds of ms per keystroke on a large session. In view 1,
assistant output stays folded, including the newest reply; streamed tool
regions appear folded in views 1/2, and the next prompt is always open.
Levels are kept monotonic (a tool is always exactly one deeper than its
enclosing assistant) so Neovim's fold tree stays valid and za/zo behave
predictably.

Above the view, <Tab> and the block-navigation keys DRILL: <Tab> opens
the fold under the cursor persistently (pins it) or closes it again;
]t/[t, ]c/[c and ]e/[e jump to the next block AND open it. Opening is
non-exclusive — opening one fold leaves previously opened folds alone.
]m/]u/]a move at message granularity without opening anything.

An open fold STAYS open: it is tracked by its fold-start line, not a
transient peek — whether it was opened with <Tab>, a navigation key, or
plain za/zo. When the conversation structure advances — a new `# @role`
heading, tool, thinking or error opener streams into the buffer — yap
reconciles only what changed, WITHOUT clearing Neovim's manual fold
state. The old zX-per-append approach closed every fold and re-opened a
handful, which collapsed the view (cursor/scroll jumps) and flickered;
instead each structural append only (1) closes folds the append newly
created that leaked open — Neovim inherits a manual foldopen into
same-or-deeper folds, so "open one tool" used to make every later tool
arrive open — and (2) re-opens the user-opened folds. Plain-text appends
change nothing, so streaming prose never touches folds, and the cursor
and scroll position stay exactly where the user left them. Typing (user
edits) likewise changes nothing.

A view keypress (<leader>1..3) is an explicit reset: it clears every
user-opened fold. Folds are keyed by line number, so they survive sends
and streaming (sends only append); an edit that shifts a fold's line
drops it. A send does NOT snap folds back to the view — manual opens and
closes persist until you change the view.

Navigation keymaps jump between headings, see |yap-keymaps|.

9. WINBAR                                                      *yap-winbar*

The winbar is the session dashboard. Left: an animated spinner beacon while
the buffer itself is streaming — once a tool has run for 2s its name and
elapsed time join the spinner (`⣾ bash 12s`) — then a raised rollup island
for ALL OTHER yap sessions: `▶N` (N other buffers streaming a reply) and
`◉N` (N other buffers await you; jump to one with |:YapInstances|). The
island appears only when at least one other session is running or waiting;
it never counts the current buffer. After the island: the session
description (truncated to 40 display columns), provider/model combo, and
the applied fold view (`Ⓕ1` agent output folded, `Ⓕ2` tools & thinking
folded, `Ⓕ3` all open — the last view applied with <leader>1..3;
manual |za| toggles don't update it). Right: three usage chips
(|yap-winbar-numbers|). A state glyph appears on the far right only when
something is wrong:

  ✗ error   The last send failed (vim.notify fired too); cleared on the
            next send.

Idle and "awaiting your reply" show no glyph — the absence of the left
spinner already tells you nothing is running.

Example: `⣾ moonshot/kimi-k3 Ⓕ2` ... `󰅐 1.5k · $0.0034 · 󰆼 12k · $0.51 · 󰊚 35k/200k · 18% █▍░░░░░░`

Reading the numbers                                    *yap-winbar-numbers*

The right side shows three chips, each led by a config icon (the `icons`
table in |yap-configuration|; set one to `""` to drop its glyph):

  󰅐 N        Since-open: total tokens (prompt + completion) and cost
             for this buffer, accumulated since it was opened in this
             Neovim. Resets when the session is reopened.
  󰆼 N        All-time: total tokens and cost for the whole session
             file, summed from every `turn_end` journal entry in the
             audit log (|yap-audit|). Survives restarts; answers "what
             has this session cost".
  󰊚 N/M · P% Context fill: the last turn's prompt size against the
             model's context window (both from the `turn_end` journal),
             plus the fill percentage and a fixed-width gauge — the "how
             full is my context" answer, e.g. `35k/200k · 18% █▍░░░░░░`.
             The gauge fill is green below 70%, amber from 70–90%, and
             red at 90% or more (`YapGaugeLow`/`Mid`/`High`; the dim
             track is `YapGaugeEmpty`). Absent until the first turn
             completes, and only for models the pricing catalog knows a
             context window for.

Suffixes are compact: `k` = thousands, `m` = millions (`1.5k` = 1,500
tokens). Costs are USD, computed as `in × input price + out × output
price` (USD per 1M tokens) — your `pricing` overrides first, then the
embedded catalog (see |yap-configuration|). On a freshly opened session
with no prior turns the two token/cost chips are equal; after a reopen
they diverge.

The bar is width-aware, so a narrow window never crowds out the parts
that matter. It drops parts in this order as the window shrinks: the
provider/model + fold-view cluster, then the chip costs, then the chip
tokens (leaving just the two prices), and finally the session
description, which truncates shorter. The error glyph, the left island
(`▶N`/`◉N`) and the two prices are the last things standing, and the
winbar re-lays itself out on `WinResized`.

The `▶N` rollup counts OTHER yap buffers with an in-flight request; the
`◉N` rollup counts OTHER yap buffers with a completed turn awaiting
your reply. Live sessions enter it when a send finishes; a reopened
session enters it when it ends on a `# @user` heading with assistant
history above it. For a global segment independent of yap buffers, use
`%!v:lua.require('harness').overview()` in a statusline or tabline.

10. LUA <-> GO PROTOCOL                                      *yap-protocol*

  stdin   one JSON line per turn: {"provider":"...","model":"...",
          "messages":[...]} (roles system/user/assistant; persisted tool
          regions arrive flattened as assistant transcript text)
  argv    yap serve (one persistent process per chat buffer)
  stdout  raw assistant text, streamed; thinking, tool blocks and usage
          wrapped in |yap-markers|. Each turn ends with an RS-prefixed
          yap:turn_end {"ok":true|false,"error":?} line (not buffer text).
          A turn is complete once the corresponding stderr turn_complete
          barrier is received, so audit events cannot lag behind completion.
          `yap send --provider NAME --model MODEL` remains available for
          one-off calls (e.g. generating a session description).
  stderr  error message, exit 1. Also carries `yap:event {json}`
          progress lines; the Lua side timestamps each one and appends
          it to the audit log (|yap-audit|), and renders it into the
          tail buffer (|:YapLive|):
            tool_start   {"type","name":"bash"|"python","log","command"} — the
                         tool's output streams into `log`; tail it for live view
            tool_end     {"type","name":"bash"|"python","log","truncated"} —
                         the tool's log is complete; the Lua side drains the
                         final bytes and removes the untruncated temp log
            tool_call    {"type","name","args"} — every tool before it
                         runs, full arguments (the buffer header keeps
                         only slimmed write/edit args, R12)
            tool_result  {"type","name","bytes","result"} — full result
            approval_request {"type","id","command"} — a dangerous command
                         pauses the turn; the Lua side prompts and replies
                         {"type":"approval_result","id","approved"} on stdin
            approval_timeout {"type","id"} — the user never answered; denied
            retry        {"type","attempt","delay_ms","error"} — a
                         transient generation error (429/5xx/network)
                         was retried before any output was emitted
            turn_end     {"type","model","prompt","completion","cost",?,
                         "context_window",?,"ms"} — one per completed send
          The Lua side also synthesizes `output` events (streamed
          bash/python output chunks) as it drains the temp log, so the audit log
          carries live output, not just the final result.
          The rest is error text.

The binary runs the agent loop internally: when the model requests tool
calls it executes them (compiled-in tools, see |yap-tools|), emits one
yap:tool region per pair, and re-sends until the final answer or the
iteration bound. In-memory only (never persisted), each iteration appends
the exact assistant message parts GoAI produced — reasoning items/encrypted
content, signatures, thought signatures, reasoning_content — plus native
tool-result messages, so tool continuation is lossless within one process.
The binary is pure Go (no cgo), built CGO_ENABLED=0, using the GoAI SDK
behind Yap's own agent/llm surface.

11. BUSINESS RULES                                             *yap-rules*

The invariants below are the design contract of this plugin. Each rule
exists for a reason; change the code and the rule together. AI assistants
editing this repository MUST keep this section up-to-date.

R1  The buffer is the only conversation state.
    Neither the Lua side nor the Go binary may keep message state between
    turns. Why: branching by deletion, prefill by editing, and undo-tree
    navigation only work if the buffer is the single source of truth.

R2  `<!-- yap:* -->` marker regions are never sent as buffer text.
    The parser skips them (thinking, error, usage, yap:ui) or flattens
    them (yap:tool becomes plain assistant transcript text naming the
    tool, its JSON arguments and result — the raw region text is still
    never sent). Why: thinking or display payloads
    re-sent to the API pollute or break the conversation. (Bug of record:
    the first error comment WAS sent back as assistant content.)

R3  Lines before the first heading are ignored.
    The session header lives there. The parser's flush must clear the
    accumulator when no role is set. (Bug of record: pre-heading text was
    prepended to the first message until this was fixed.)

R4  The binary emits plain text and yap markers only. No ANSI, no
    padding, no rendering. Why: markdown rendering is the user's
    ft=markdown setup; cell-based TUIs break Neovim yanking.

R5  The binary talks to providers through the GoAI SDK behind Yap's own
    agent/llm adapter: native OpenAI (Responses API), Anthropic,
    Google/Gemini and DeepSeek, plus any OpenAI-compatible
    /chat/completions endpoint (Moonshot/Kimi, OpenRouter, z.ai, local
    servers) via the compat provider. The stdout wire protocol is
    unchanged: plain text and yap markers.

R6  Adjacent same-role blocks are merged on send; empty blocks dropped.
    Why: providers require role alternation.

R7  Exactly one blank line between message blocks, enforced LOCALLY at
    every write: structural appends (headings, error markers) go through
    append_block(), which trims trailing blanks and prepends exactly one
    blank line itself — never append a heading with append_text(). The
    binary separates streamed tool blocks with blank lines. There is no
    buffer-wide normalize pass: sends never rewrite existing lines, so
    what you see before ctrl-s is byte-identical to what gets sent.
    Binary-emitted blocks (thinking, tool regions, error markers) carry
    no leading newlines and self-terminate with exactly one blank line;
    a pad() in the agent loop bridges the two stateful transitions
    (heading → first block, streamed text → first tool header).
    (Bug of record: blocks prepended \n\n while regions also ended in
    \n, giving two blank lines between tool calls.)
    Why: readable diffs, stable folds, gptel-like staticness.
    (Bug of record: hand-rolled "\n" prefixes broke separation when
    trailing-blank trimming was added; a buffer-wide normalize pass made
    every send rewrite the whole buffer and churn fold state.)

R8  Sessions are plain markdown files; file operations are the session
    operations. The file is created at buffer creation so a fresh chat is
    file-backed (and nameable via :file) before the first reply. Autosave
    only after a COMPLETED reply (never on error). Autosaves go through
    :write! (not writefile()): the buffer owns the file, so mtime
    bookkeeping, :w, and E13 all behave normally. Every stream exit,
    including backend errors and :YapStop, repairs any dangling streamed
    marker, appends a fresh `# @user` block, and saves that final writable
    state. save() follows buffer
    renames so :file names and :saveas forks. Why: no second
    serialization format to keep in sync. Session buffers (and their
    tail buffers) are unlisted — never in |:ls| or buffer pickers — so
    navigation is |:YapInstances|, and a session's
    tail opens with |:YapLive|.

R9  Errors surface three ways: vim.notify (transient), winbar error state
    (persistent until next send), and a parse-excluded buffer marker
    (record). Spawn failures of the binary are caught and reported the
    same way.

R10 View levels: <leader>1 folds all agent output (only user prompts
    stay open), <leader>2 folds tool calls and thinking only, <leader>3
    unfolds everything; the system prompt stays folded in views 1 and 2
    and opens in view 3. Fold levels are role-dependent — user messages
    1, assistant messages 2, tool/thinking/error regions and the system
    prompt 3. View 1 leaves the newest reply folded too; auto-opening it
    caused a brief open/close flicker as the reply completed. Levels stay
    monotonic (tools remain nested in assistant folds) so Neovim's fold
    tree and za/zo work. The three views are pure 'foldlevel' (1, 2, 3)
    with no manual foldclose: manual closes plus expr folds made Neovim
    re-evaluate every fold on each edit (hundreds of ms per keystroke on
    a large session). View 2 is applied ONLY when a session buffer is
    opened. <Tab>, the block-navigation keys and plain za/zo drill by
    opening a fold (non-exclusive): the open is keyed by its fold-start
    line and survives sends/streaming. On a structural append (heading,
    tool, thinking, error) the send path reconciles WITHOUT zX: it
    closes only newly created folds that leaked open (Neovim inherits a
    manual foldopen into same-or-deeper folds), and re-opens user-opened
    folds. zX was dropped because it collapsed the whole view and
    flickered every append; plain-text appends now change nothing and
    the cursor/scroll stay put. A view keypress clears all manual opens.
    Typing (user edits) still changes nothing. A send no longer snaps
    folds back to the view — manual opens AND closes persist until the
    view changes. The winbar Ⓕ chip shows the last APPLIED view, not
    measured fold state (measuring made <leader>3 read Ⓕ0).

R11 Streaming appends at the end of the buffer, fully async (gptel-style:
    the buffer stays editable while a reply streams in). Editing above the
    streaming block is safe; typing inside/below it interleaves with the
    stream. Accepted trade-off; the fix (extmark insertion point) is
    documented as future work, not done.
    A window whose cursor sits on the last line FOLLOWS the stream (the Lua
    side re-pins the cursor to the end after every append; Neovim never
    scrolls a window for an API edit, so without that the view only tracked
    the end while a chunk happened to land exactly on the cursor, i.e. while
    the last line was empty, and then stranded it mid-reply). A window
    scrolled away is NEVER dragged during the stream, and nothing moves from
    a non-normal mode. (The one deliberate exception, unchanged: a completed
    turn puts the cursor on the new `# @user` heading, so the next prompt is
    ready to type.)

R12 One buffer region = one tool call+result pair.
    A yap:tool region holds the call (single-line JSON header) and the
    result text together; parsing flattens the region into plain assistant
    transcript text (tool name, JSON arguments, result). Deleting or
    editing the region edits that transcript directly, so persisted history
    never carries native tool_calls/tool messages — those exist only in
    memory during a single send. Result content policy: edit/write tools
    return short confirmations,
    read-like tools return truncated content (pi: 2000 lines / 50KB);
    pretty payloads (diffs) go in parse-excluded yap:ui subsections.
    write/edit headers are slimmed at emission time (`[N lines]` for
    content, `[N edits, +A/-B lines]` for edits): the header is the tool
    name and JSON arguments the model sees flattened into its history, and
    kilobytes of file content
    there buy nothing the yap:ui diff and the file on disk don't
    already show (Anthropic's clear_tool_inputs is the same idea); the
    full arguments are in the audit log. Old result bodies can be
    cleared explicitly with |:YapClear|.

R13 No MCP. The author's tools are thin HTTP wrappers that are less code
    as native Go functions than an MCP client; MCP also has no equivalent
    of pi's hook bus. If ever needed, add mark3labs/mcp-go additively.

R14 The model state is durable YAML frontmatter; everything else is
    ephemeral.
    The frontmatter holds `provider`/`model` (the combo to resume with),
    `models` (the ordered history of combos used), and `created_at`/
    `updated_at` timestamps. yap writes the model fields only on :Yap and
    |:YapChangeModel| — never during a send, so R7's append-only rule holds —
    and stamps `updated_at` on every save (one line after the turn, not
    per-reply metadata). It reads the block on open and surfaces it in the
    |:YapSessions| picker. Token/cost totals
    are deliberately NOT
    frontmatter: they accumulate in per-buffer memory for the winbar
    and reset on reopen. The earlier frontmatter design got this wrong
    by folding per-reply usage into the header, which made every
    metadata update a non-local buffer edit that fought R7.

R15 Tools are compiled-in Go files, one per file in agent/tools/.
    Each file self-registers via init(); adding a tool = adding a file
    and recompiling. Not config files (the author wants tool code, not
    opaque declarations), not subprocesses (recompiling is accepted and
    the binary stays self-contained). bash, python and ssh are
    deliberately unsandboxed — the author runs pi the same way and
    accepts the residual risk — but are no longer unconfirmed: a
    conservative denylist of irreversible / high-blast-radius
    operations (piped-into-shell, rm -rf, mkfs/dd onto block devices,
    sudo, git push --force / reset --hard / clean -f, chmod -R /
    chown -R, redirects onto system or secret paths, shutdown/reboot,
    fork bombs; for python, subprocess/os.system/... and
    shutil.rmtree) pauses the turn for an explicit human Run/Deny
    before the command executes. Denial, timeout, and the absence of a
    serve process (yap send) all deny. This is a prompt-injection
    mitigation, NOT a security boundary: the denylist is bypassable. A
    real sandbox, if ever wanted, is bubblewrap (Codex's Linux
    choice), not command-pattern allowlists (documented as bypassable).
    bash/python's operational mechanics are unchanged: own process
    group, group kill on timeout and on :YapStop, tail-truncation,
    closed stdin.

R16 Live tool output never enters the chat buffer.
    The buffer is the parseable conversation document (R1); streaming
    command output into it forces incremental escaping, dangling-region
    repair and post-turn dedup (the yap:stream/keepstream design this
    rule replaced). Instead each session has ONE persistent tail buffer
    (yap://<session>-tail): bash/python announce their temp log via a
    yap:event stderr line, the Lua side drains new bytes into the
    tail (a `$ command` header per call), and :YapLive opens it. The
    drained bytes are recorded in the audit log as `output` events, and
    the tail buffer is rebuilt from that log on reopen — there is no
    separate tail file. The chat buffer only gets one-shot, append-only
    writes: the tool header
    when the call commits, the result when it finishes. Normal streaming
    is append-only; explicit document operations may rewrite existing
    content: |:YapClear| replaces old tool result bodies with a pointer
    to the audit log (path plus the exact line range holding that
    call's record), |:YapCompact| can delete superseded history after
    confirmation, frontmatter changes with the selected model, and the
    transient yap:usage marker is consumed into in-memory totals. Why:
    output exists in exactly one place at
    any moment, and the buffer format has no transient states to repair.

R17 The audit log is the durable record of everything the context
    doesn't carry. ~/.yap/audit/<cwd-slug>/<session>.jsonl, JSON Lines
    (one timestamped JSON object per line), append-only, written by the
    Lua side from yap:event lines plus synthesized `output` events for
    streamed bash/python output: full tool arguments, streamed
    bash/python output, full results, and one journal line per turn
    (model, tokens, cost, ms). The tail buffer (|:YapLive|) renders
    these events and is rebuilt from the file on reopen; the audit file
    is the authoritative record and survives restarts.
    This is what makes slimmed headers (R12) and |:YapClear|
    lossless.

R18 Templates and skills are plain markdown files inserted into the buffer.
    `templates_dir` files append as a `# @user` message: a body with
    no leading heading is wrapped automatically; a leading `# @role`
    heading (including `# @user`) is used as-is to set the role, and
    append_message reuses the trailing heading when it already has that
    role, so a `# @user` heading never duplicates.
    `skills_dir` files merge into the `# @system` block and so carry
    no `# @user`/`# @assistant` headings of their own (except an agent
    skill that quotes the message format). A skill's optional frontmatter
    may carry `description:` for the skills intro (skills_intro) and is
    stripped on insert. Nothing is auto-loaded and nothing is hidden:
    the inserted text is visible, editable buffer content like any
    other, and the intro is a short visible list, never injected bodies.
    Why: the buffer stays the only state (R1), and templates/skills are
    just text, so one insert command covers compaction, snippets and
    skills.

R19 Turn completion is a first-class event.
    When the binary exits successfully, the Lua side emits
    `User YapTurnDone` with `data = { buf, turn }` (turn is the binary's
    `turn_end` payload when usage was reported: model, prompt, completion,
    cost, ms). Hard backend/spawn errors do not emit the event. A successful
    binary exit can still contain an agent error marker (for example an
    empty completion or the tool-iteration bound); that state is surfaced
    as an error and the default completion notification is suppressed.
    The default handler (installed
    by setup(), disabled with `notify_done = false`) calls vim.notify —
    only for a buffer the user isn't looking at, and never on the error
    path, which already notifies (R9). A completed turn sets the
    awaiting hint, which drives the `◉N` rollup counting the OTHER
    awaiting buffers (the winbar itself shows no glyph for it): an
    imperative UI hint like `errors`/`yap_usage`, not conversation state
    (R1); reopened sessions seed the rollup from their content on open. Why:
    herdr's "working → blocked → idle" notification is
    a completion *event*, and an autocmd is the Neovim-native hook for
    it (noice/nf-notify, chaining a next send) instead of a hardcoded
    side effect.
