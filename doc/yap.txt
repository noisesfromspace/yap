1. INTRODUCTION                                          *yap-introduction*

yap is an LLM chat plugin where the conversation lives in a plain, editable
markdown buffer. A small Go binary (`yap`) handles provider requests and the
agent/tool loop: it reads the message array on stdin and streams the reply
to stdout. There is no TUI, and no hidden conversation state between turns.

To install: build the binary and put it on Neovim's PATH (see the README),
configure a provider in ~/.config/yap.json, then
`require("harness").setup({...})` and run `:Yap`.

- Deleting a region removes it from the conversation: that is branching.
- Editing an assistant reply changes what the model "said".
- Writing your own `# @assistant` message steers the model (prefill).
- Yanking, undo, folds and rendering are just Neovim. `:undotree` is a
  branch navigator.

Contributors: the Lua <-> Go wire protocol and the numbered design rules
live in CONTRIBUTING.md, not here.

2. SETUP & CONFIGURATION                                *yap-configuration*

Lua setup (defaults shown; substitute your own provider/model): >lua

  require("harness").setup({
    bin = "yap",                  -- path to the Go binary
    provider = "moonshot",        -- example; use your provider
    model = "kimi-k3",            -- example; use your model
    models = {                    -- optional: combos for the model picker
      "moonshot/kimi-k3",
      "deepseek/deepseek-v4-pro",
      "openai/gpt-5.6-sol",
    },
    system = "You are a helpful coding assistant. Answer concisely.",
    agents_file = vim.fn.expand("~/.config/yap/AGENTS.md"),
    agents_dir = "~/.yap/agents",       -- subagent definitions
    sessions_dir = "~/.yap/sessions",   -- autosaved sessions + scratch queues
    audit_dir = "~/.yap/audit",         -- audit logs
    notify_done = true,           -- vim.notify when a hidden turn finishes
    description_model = "openai/gpt-5-nano",       -- on-send label
    description_answer_model = "openai/gpt-5-mini", -- final session title
    syntax_highlight = true,      -- keep markdown syntax colors (default)
    nerd_font = true,             -- false for plain-Unicode icons
    icons = { since = "󰅐", total = "󰆼" }, -- winbar/picker glyph overrides
    keymaps = { stop = "<C-c>" }, -- override any key; "" disables it
  })
<

`agents_file` is the system prompt for new buffers and is read per buffer, so
edits apply to the next session. When missing or empty, `system` is used. The
path is used verbatim (no `~` expansion); the default is
`$XDG_CONFIG_HOME/yap/AGENTS.md` (or `~/.config/yap/AGENTS.md`).

`agents_dir`, `sessions_dir` and `audit_dir` locate yap's data under
`~/.yap/`. A leading `~` is resolved against the real home directory — never
the current working directory — and an absolute path is used verbatim, so an
unset, empty, or relative `$HOME` must not make yap write its `.yap` folder
into the project. Defaults: `~/.yap/agents/`, `~/.yap/sessions/`,
`~/.yap/audit/`.

The harness always prepends its own `# About Yap` boilerplate (buffer
semantics, marker rules) as the first system message of every turn. It is
independent of `agents_file` and never written into the session file, so the
`# @system` message stays clean.

`notify_done` (default true) fires `vim.notify` when a turn completes in a
buffer not visible in any window. The turn's `turn_end` payload (model,
tokens, cost, ms) is attached to the `User YapTurnDone` autocmd so other
plugins can hook completion (noice/nf-notify rendering, chaining a next
send). Delegated children report to their running parent instead of producing
duplicate toasts; a direct follow-up in a child still notifies when hidden.
Disable with `notify_done = false` and hook the same event yourself.

`syntax_highlight` (default true) keeps tree-sitter's markdown syntax
highlighting on session buffers; set false to drop syntax colors. The
highlighter is incremental and measured to be effectively free, so the
default keeps colors on.

`icons` sets the UI glyphs for the winbar and session picker
(|yap-winbar|). Keys: `since`, `total`, `running`/`waiting`/`stopped`/
`error`/`idle`/`done`, `steer`, `approval`, and the rounded caps
`cap_l`/`cap_r`.
Defaults are Nerd Font v3 glyphs; `nerd_font = false` selects plain-Unicode
icons, the typographic spinner and the block gauge. Explicit `icons`
overrides still take precedence. Set an individual icon to `""` to drop it.

`relativenumber` is left alone: session buffers keep your setting. yap sets
the buffer-local `minidiff_disable` flag (and detaches mini.diff if it already
attached) so diff hunks — meaningless on a transcript — don't re-render the
gutter on every redraw.

`keymaps` maps each action to its key sequence, so any binding in
|yap-keymaps| can be rebound from `setup()`. Keys: `send`, `stop`,
`change_model`, `change_default_model` (global), `live`, `scratch`, `insert`,
`insert_here`, `insert_file`, `sessions` (global), `waiting` (global),
`history` (global), `history_renamed` (global), `help`,
`next_message`/`prev_message`, `next_user`/`prev_user`,
`next_assistant`/`prev_assistant`, `next_tool`/`prev_tool`,
`next_think`/`prev_think`, `next_error`/`prev_error`, `view_1`..`view_3`,
`toggle_fold`, `inner_message`, `around_message`, `inner_region`,
`around_region`. Buffer-local keys apply when a session opens (and on resume);
the global ones are installed once by `setup()`. Set an entry to `""` to
disable it.

The session description shown in the winbar (|yap-winbar|) and session
picker is generated in two stages sharing one `description:` frontmatter key.
`description_model` (default `openai/gpt-5-nano`) supplies an instant label
from the first useful request when you start a session; it does not relabel
every follow-up. `description_answer_model` (default `openai/gpt-5-mini`)
writes an overall title after each completed turn, based on the user's
requests in order, with the first request anchoring the session goal. Routine
commit/close requests are excluded, and assistant/tool output is never title
context. Set either to "" to disable that stage; the description survives in
the frontmatter either way.

`templates_dir` and `skills_dir` (defaults `~/.config/yap/templates/` and
`~/.config/yap/skills/`) hold the plain-markdown files inserted by
|:YapInsert|; `skills_intro` (default true) adds a `## Skills` list of
name + description to new sessions for discoverability. See |yap-templates|.

Config and runtime data:

  ~/.config/yap.json   Providers and optional pricing: >json

    {
      "providers": {
        "moonshot": { "base_url": "https://api.moonshot.ai/v1",
                      "api_key_env": "MOONSHOT_API_KEY" }
      },
      "decision": { "base_url": "https://openrouter.ai/api/alpha/decisions",
                    "api_key_env": "OPENROUTER_API_KEY",
                    "model": "typesafe/jev-1.13" },
      "alert": { "approval_prob": 0.7, "advisory_prob": 0.35,
                 "min_confidence": 0.6 },
      "pricing": { "kimi-k3": { "input": 0.60, "output": 2.50 } }
    }
<
  Any OpenAI-compatible /chat/completions endpoint works. API keys come from
  the named env vars. `pricing` (USD per 1M tokens) overrides the embedded
  catalog for a model — needed only for models the catalog misses or a
  provider whose price differs. `decision` configures the decision-model
  backend behind the jev tool and the alert gate (|yap-alert-gate|); it
  defaults to Jev via OpenRouter's Decisions API, OPENROUTER_API_KEY, and the
  pinned `typesafe/jev-1.13` release. `alert` tunes the pre-execution alert
  gate: `approval_prob` / `advisory_prob` / `min_confidence` are decision
  thresholds; any zero value falls back to a conservative default.

  ~/.config/yap/AGENTS.md   Default system prompt (see above).
  ~/.yap/sessions/          Autosaved sessions + scratch queues (|yap-sessions|).
  ~/.yap/audit/             Audit logs (|yap-audit|).
  ~/.yap/agents/            Subagent definitions (|yap-tools|).

3. COMMANDS                                                  *yap-commands*

Commands are intentionally quiet on success: visible edits, the winbar and
pickers confirm ordinary actions. Warnings and errors still notify; actions
that need a decision (such as |:YapCompact|) still prompt. All commands act on
the current buffer unless otherwise noted.

*:Yap*
:Yap                  Open a new session buffer with a system message and an
                        empty `# @user` prompt. Nothing is sent until you type
                        there and |:YapSend|.
*:YapSend*
:YapSend              Send the whole buffer to the provider and stream the
                        reply in. Each send also injects Neovim's current
                        working directory as request-only context (evaluated
                        at send time), so `:cd` takes effect on the next send.
                        Not written into the session buffer.
*:YapAttach*
:YapAttach            Optional: on a line containing only a dropped PNG/JPEG
                        path in a user message, import it immediately into
                        Neovim's data directory and replace it with a
                        `![FILE: name](file:///...)` reference. Normally no
                        command is needed: on :YapSend standalone absolute
                        PNG/JPEG paths in user messages are imported first.
                        A typed path has the same effect as a dropped one.
                        The backend sends the image bytes (up to 10 MiB) plus
                        its filename, detected media type, byte size and
                        pixel dimensions when decodable to the model. Keep the
                        asset store when moving sessions; delete the reference
                        to stop sending the photo.
*:YapStop*
:YapStop              Kill the in-flight request for the current buffer.
*:YapLive*
:YapLive              Open this session's audit view (|yap-audit|): one
                        persistent yap://<session>-audit buffer rendering the
                        audit log as it streams — a `$ command` header per
                        bash call with its drained output, one journal line
                        per non-bash tool call and result, and one journal
                        line per turn. Opens in a split scrolled to the
                        bottom, or focuses the existing window; never opens by
                        itself. It is a rendering, not a second log: rebuilt
                        from the log on reopen, so it survives restarts.
*:YapAlerts*
:YapAlerts            Pick an advisory or approval request from this
                        project's saved sessions and open its entry in
                        :YapLive. Includes closed sessions; newest first.
*:YapApproval*
:YapApproval          After choosing Inspect in a Run/Deny dialog, answer
                        Run, Deny, or Inspect again from the conversation or
                        audit. Inspect focuses the shield-marked request with
                        the triggering tool call directly above it and the
                        conversation alongside. Dismissal denies; the backend
                        also denies after five minutes.
*:YapClear*
:YapClear [keep]      Replace the result bodies of all but the last [keep]
                        (default 2) yap:tool regions with a one-line
                        placeholder naming the exact audit-log lines
                        (path:line-range) where the removed output lives.
                        Headers and yap:ui diffs stay; the full output is in
                        the audit log (|yap-audit|). The cheap alternative to
                        compacting the conversation.
*:YapCompact*
:YapCompact           Compaction as one command: insert the compact prompt (a
                        `compact` template in templates_dir, or a built-in
                        prompt), send, and — once the summary has streamed in
                        — offer to delete the superseded history. The summary
                        stays a visible # @assistant turn; deletion is an
                        undoable buffer edit (|yap-compact|).
*:YapInsert*
:YapInsert [name]     Insert a template or skill (|yap-templates|). With no
                        argument, pick from a combined list. At the cursor,
                        use `<leader>T`.
*:YapChangeModel*
:YapChangeModel {provider/model}
                        Change this buffer's provider/model combo. Without an
                        argument, pick a combo via vim.ui.select, filled from
                        setup({ models = ... }) when configured, else by
                        querying every provider in config.json (cached for
                        the session). Mid-turn, the new combo takes effect at
                        the next model boundary and leaves a
                        `<!-- yap:model ... -->` marker; native tool history
                        is kept, so no stop-and-resend happens. A combo that
                        fails to resolve becomes a `<!-- yap:error -->` marker
                        and the turn keeps its current model. To change the
                        default for new buffers, use `<leader>M`.
*:YapFork*
:YapFork [name]       Copy the current in-memory conversation (including
                        unsaved edits) into a new, independent session in the
                        same project, regardless of |:pwd|. The original
                        buffer, file and running state stay attached to the
                        original; the copy opens in the current window. No
                        name generates a filename; a name uses `name.md`.
                        Existing files are never replaced. Mid-turn, only
                        through the last completed reply is copied. To branch
                        from an earlier turn, fork first, then delete the
                        later turns before sending. The source's `forks` and
                        the copy's `forked_from` frontmatter link them.
*:YapSessions*
:YapSessions [scope]  Pick a saved session to resume. scope is `cwd` (the
                        default, current project), `all` (every project), or
                        `renamed` (sessions named with |:file|, plus their
                        forks and subagents). Sessions still on their
                        auto-generated filename are hidden unless they have
                        subagents, are unnamed forks, or hold an unsent
                        `# @user` prompt. Saved subagents appear beneath their
                        parent; orphan children show `(parent not shown)`.
                        Open sessions are unlisted (absent from |:ls|); use
                        `<leader>r`.

4. KEYMAPS                                                    *yap-keymaps*

Set only in yap buffers, except <leader>r, <leader>w, <leader>y, <leader>R
and <leader>M, which are global (they list sessions or change the default
model, so they work from any file). Every binding is a `keymaps` config key
(see |yap-configuration|); the defaults are shown below.

  <C-s> (n, i)          Send the buffer. The reply streams in.
  <C-c>                 Kill the in-flight request (see |:YapStop|).
  <leader>m             Change model (picker, see |:YapChangeModel|).
  <leader>M             Change the default model for new buffers (picker).
  <leader>l             Watch the audit view (see |:YapLive|). Also mapped
                        in the scratch queue.
  <leader>s             Toggle the scratch buffer (see |yap-sessions|).
  <C-t> (n, i)          Insert a template or skill (see |:YapInsert|).
  <leader>T             Insert a template or skill at the cursor.
  <leader>i (n)         Pick a file under the current |:pwd| and insert an
                        `@path` reference at the cursor. Also mapped in the
                        scratch queue.
  <leader>r             Pick an open session (instances()).
  <leader>w             Pick a session awaiting a reply or manually stopped
                        (waiting()).
  <leader>y             Pick a saved session to resume (history()).
  <leader>R             Pick only renamed history sessions.
  g?                    Show the current Yap shortcuts in a searchable
                        floating window; use `/`, `n` and `N`.
  <Tab>                 Toggle the fold under the cursor.
  ]m  [m                Next / previous message heading.
  ]u  [u                Next / previous user message.
  ]a  [a                Next / previous assistant message.
  ]t  [t                Next / previous tool call or thinking region (opens it).
  ]c  [c                Next / previous thinking region (opens it).
  ]e  [e                Next / previous error region (opens it).
  <leader>1             Fold all agent messages; user prompts stay open.
  <leader>2             Fold all tool calls and thinking regions.
  <leader>3             Unfold everything.

  Text objects (operator-pending and visual mode):
    im / am             inner / a message — the body without its `# @role`
                        heading, or the whole message. `cim` replaces a
                        message body; `dam` drops a message.
    it / at             inner / a thinking, tool or error region — the content
                        without its markers, or the whole region. `dit` clears
                        a region, `dat` removes it.

View 2 is the default for opened session buffers; the system prompt stays
folded in views 1 and 2. See |yap-folding|.

5. BUFFER FORMAT                                                *yap-buffer*

A yap buffer is plain markdown. Headings delimit messages: >

  # @system
  # @user
  # @assistant

Everything between headings is message content. Everything before the first
heading is ignored by the parser — that is where the session's model state
lives, as YAML frontmatter: >

  ---
  model: kimi-k3
  provider: moonshot
  created_cwd: /opt/code/yap
  turns: 14
  created_at: 2025-09-29T19:22:33Z
  updated_at: 2025-09-29T19:24:01Z
  models:
    - moonshot/kimi-k3
    - deepseek/deepseek-v4-pro
  subagents:
    - /home/martijn/.yap/sessions/.../session-a1b2c3.md
  assets:
    - <sha256>.png
  ---
<

`provider`/`model` is the combo to resume with; `created_cwd` is the exact working
directory the session was created in (the session-dir slug is lossy, so this
is the only exact record); `models` is the ordered history of every combo
used (most-recent-last); `subagents` lists subagent session paths
(most-recent-last); `assets` is the manifest of content-addressed photo files
this session references (see |yap-attach|); `created_at` / `updated_at` are
timestamps; `turns`
counts completed `# @assistant` replies so the picker can show depth without
opening the file. The frontmatter is the ONLY durable session state: yap
writes the model fields on :Yap and |:YapChangeModel|, stamps `updated_at` on
every save, reads it on open, and sends never rewrite it mid-turn. Token/cost
totals are NOT stored here — the winbar accumulates them per-buffer
(|yap-winbar|) and the durable session total is derived from the audit log
(|yap-audit|). Legacy files without frontmatter keep the setup() default
combo.

The active combo comes from the frontmatter on open, then per-buffer vars set
by |:YapChangeModel|, then the persisted default, then setup() defaults.

A yap buffer never attaches a language server: the buffer is the conversation,
and a markdown LSP's semantic-token/inlay-hint stream is pure per-redraw cost
on a large session; an LspAttach guard stops any markdown client.

6. MARKERS & TOOL REGIONS                                      *yap-markers*

HTML comment regions of the form `<!-- yap:<word>` ... `-->` are shown in the
buffer but NEVER sent to the provider as buffer text; the parser skips them
(one exception: yap:tool, which is FLATTENED into assistant transcript text).

  <!-- yap:thinking   Provider-exposed reasoning (or reasoning summaries)
                        streamed by GoAI. Folded away with the assistant
                        message and never persisted in history.
  <!-- yap:error      Backend error record, left after a failed send.
  <!-- yap:usage      Token usage reported at end of stream. Consumed
                        immediately: folded into the winbar totals and the
                        line removed.

Tool regions                                                *yap-tool-region*

A tool call and its result are ONE region inside an assistant message: >

  <!-- yap:tool {"id":"call_1","name":"edit","arguments":{...}} -->
  Successfully replaced 1 edit(s) in main.go.
  <!-- yap:ui -->
  ```diff
  @@ -10,3 +10,3 @@
  -old line
  +new line
  ```
  <!-- /yap:ui -->
  <!-- /yap:tool -->
<

  Header          The complete call as JSON. Single-line when short (≤ 120
                  chars); otherwise pretty-printed multi-line JSON between
                  `<!-- yap:tool` and `-->`. Multi-line headers fold closed by
                  default (a `▸ tool: <name>` foldtext) since the yap:ui diff
                  below is the visual record.

  Result text     Exactly what the model received. edit/write tools return
                  short confirmations; read-like tools return (truncated)
                  content. Normally the header lands BEFORE the tool runs,
                  so its arguments are visible during execution. In a
                  parallel read-only round, calls run together and their
                  completed regions are emitted in original call order.
                  Live bash output is followed via |:YapLive|, never written
                  into the buffer.

  <!-- yap:ui   Optional display-only payload: a rendered unified diff for
                  edits and writes (creates included, as an all-`+` diff),
                  fenced as ```diff between paired one-line markers. Block
                  level — unlike thinking, not an HTML comment — so treesitter
                  injects the diff parser for real +/-/@ highlighting.
                  Parse-excluded like thinking: editing or deleting it changes
                  nothing. Pure decoration.

parse_buffer flattens the region into ordinary assistant transcript text: the
tool name, its JSON arguments, and the result — never native
tool-call/tool-result messages. Editing or deleting the visible markdown
changes the transcript directly. A region outside an assistant message is
skipped; a missing/empty result yields an empty labelled result; a malformed
header skips the region with a notification.

Marker regions close on a line that is exactly `-->`; content merely
containing it never closes early for OUR parser, but markdown renderers are
character-based and would, so the binary neutralizes every `-->` to `-- >`
inside comment regions. Elsewhere, a tool-result line starting with a yap
marker opener becomes `\<!-- yap:…`, and `<style>`/`<script>` open tags become
`\<style` / `\<script` — renderers show the literal text and the
line-start-anchored parser never matches.

Tool RESULTS from content-bearing tools (read, bash, ls, fetch, curl, git,
search, glob) are wrapped in a fenced code block — read with a language info
string detected from the path, fetch as ```markdown, the rest as a plain
fence. The fence is one backtick longer than any run inside the result, so a
``` line in the content can't close it early; the same fenced string goes to
the model, so the buffer and the replayed history stay identical across turns.
write/edit return short confirmations and stay bare.

7. SESSIONS                                                  *yap-sessions*

A session is the conversation markdown written to a file, plus a small set
of sibling sidecar files that carry what the conversation does not: an
append-only audit log, an optional scratch notes file, and any photo
attachments in a shared asset store. The markdown file IS the conversation —
the buffer is the only serialization of the message history — but a session
is a small file set, not a single file. Files live under
~/.yap/sessions/<cwd-slug>/ and are saved after every turn exit, including
backend errors and stops. The file is created when the buffer opens, so a
fresh session is file-backed from the start and nameable with |:file| before
the first reply; every save goes through |:write|, so 'modified', |:w| and the
exit prompt behave like any normal file buffer. The audit log
(<session>.jsonl) is written in the audit dir (|yap-audit|) and follows the
session name across |:file| renames. The scratch notes file
(<session>.notes) sits beside the session file. Photo attachments live in a
content-addressed asset store under Neovim's data directory; the frontmatter
`assets` list records which assets a session references.

Opening a session file directly — plain |:edit| or `nvim <file>.md` — is
recognized and adopted as a managed session (unlisted, keymapped, audit view
attached), the same as |:YapSessions| resume.

File operations are the session operations:

  :file new-name.md     Rename/name the active session; the picker shows the
                        chosen name. Yap moves the audit log after a
                        successful turn and the scratch queue when next
                        toggled.
  :saveas copy.md       Save the current conversation to a new session file
                        and continue in that buffer as the copy. The old file
                        is left unchanged, and its audit log and scratch
                        queue are COPIED (not moved) to the new name, so the
                        copy continues with full history while the original
                        keeps its own. Use |:YapFork| to branch into a
                        separate buffer without touching the source.
  delete a region + send  Branch the conversation within the active session.

SCRATCH BUFFER

<leader>s toggles the scratch buffer — a file-backed sibling
(<session>.notes) with three independently foldable sections:

  # @notes    An inert backlog; never sent.
  # @steer    A replaceable pending message for the RUNNING turn. <C-s>
              submits it; it stays until delivered and can be revised or
              canceled. If it misses the last model boundary or the turn is
              stopped, it remains a draft with a warning (never auto-sent).
  # @queue    Sent whole as one message on <C-s> while idle, and cleared only
              after the send starts. Queued work never auto-dispatches after
              a turn.

Consumption reads and edits the live buffer, then saves the result to the
sidecar file. Steering inserted from a template without a scratch buffer is
left in the user prompt if it was not delivered.

AUDIT LOG                                                        *yap-audit*

The session file holds the context; the audit log holds everything the
context doesn't carry. ~/.yap/audit/<cwd-slug>/<session>.jsonl — append-only,
survives restarts, one JSON object per line (JSON Lines), timestamped by the
Lua side as each event arrives:

  tool_call       every tool before it runs, FULL arguments (id matches the
                  buffer's tool header)
  tool_start      bash/python's temp log path (`command` is secret-scrubbed)
  output          streamed bash/python output chunks (synthesized as drained)
  tool_result     full result
  attachment      an image import on |:YapAttach| / |:YapSend| (source,
                  asset path, size, format, sha256) or a failed import
                  (error plus the attempted source)
  approval_request / approval_result / approval_timeout
                  the alert gate paused a call for approval; the human's
                  answer. `reason` names the deterministic category or carries
                  the jev verdict so false positives can be identified.
  alert_advisory  the gate ran a call with a warning (reason, P(harmful),
                  categorized severity, and confidence)
  retry           a transient generation error (429/5xx/network) was retried
                  before any output was emitted
  turn_end        model, prompt, completion, cost, ms — one per completed send

The audit view (|:YapLive|) is the human-readable rendering of these events
and is rebuilt from the file on reopen. A shell tool call appears before the
gate's shield-marked approval request, even if it is denied and never
produces a tool_start; a running shell call also has a `$ command` header when
execution begins. |:YapAlerts| picks an advisory/approval request and jumps
straight to its unfolded entry; entries remain available after restarts.
Structural lines are highlighted (turn headers, `$ command`, `• tool`,
timestamps); streamed and returned text stays the default color.

Each completed turn folds back to its header line — a table of contents —
while the open turn stays expanded so live output is visible. `<Tab>` toggles
a folded turn; `<leader>1`/`<leader>2` fold/unfold all completed turns. The
view only follows new output when already near the bottom. |:YapClear|
placeholders correlate a region's tool-call id with its
tool_call..tool_result line range, so a cleared body points back to exactly
what it replaced.

This is what makes the slimmed write/edit headers and |:YapClear| lossless:
anything removed from the context exists here verbatim, machine-readable. The
audit directory is created mode 0700 (the log holds full arguments and
results).

8. FOLDING & NAVIGATION                                        *yap-folding*

`# @role` headings are folds; a closed fold shows the role and the first
content line. A whole yap:tool region (header, result and ui diff, both header
forms) folds to one `▸ tool: <name>` line; thinking and error comment regions
fold likewise.

Three views, bound to <leader>1..3, each applied unconditionally so a
keypress always lands on the same state:

  <leader>1   only user prompts stay open
  <leader>2   conversation open, tool calls and thinking folded (default)
  <leader>3   everything unfolded

The system prompt is reference material: it stays folded in views 1 and 2 and
opens with everything else in view 3 (or earlier with za). View 2 is the
initial default. Each window owns its selected view and open/closed choices.
View 1 folds assistant messages and the system prompt; view 2 folds regions
and the system prompt; view 3 removes all folds. Opening an assistant in view
1 reveals its entire contents (no nested folds). The parser respects fenced
code and multiline comments.

<Tab> toggles the region under the cursor. ]t/[t, ]c/[c and ]e/[e jump to and
open a region without closing earlier ones. Clicking a closed fold opens it
(the same choice as <Tab>); clicks elsewhere keep their normal mouse behavior.
Native za/zo/zc, zA/zO/zC and zR/zM/zr/zm update the same state; closing a
previously opened region is just as persistent as opening it. ]m/]u/]a only
navigate. Message navigation and
the message text objects follow the same structural parse as folding, so a
`# @user` line inside a fenced tool result is literal content, never a message
boundary; region navigation does the same for `<!-- yap:tool` or
`<!-- yap:thinking` lines inside a fenced result.

A view supplies defaults; your choices override them for individual regions.
An open region stays open while its own contents grow, and new regions follow
the view, not the state of their neighbours. Region identity uses moving
extmark anchors rather than line numbers, so inserting lines above a region
cannot transfer its choice to another region; deletion invalidates the
identity and undo restores it. Folds are installed synchronously on returning
to a hidden session; new hidden output still follows its view. A view keypress
resets this window's choices only. Choices last while the buffer is loaded.

9. WINBAR                                                      *yap-winbar*

The winbar is the session dashboard. Left: the buffer's own state icon —
idle, awaiting your reply, stopped, error, or done (a finished subagent) —
centered in the line-number
gutter, or, while streaming, an animated beacon that escalates with how long
the running tool has been grinding (a typographic sparkle with
`nerd_font = false`). When the window is inactive the beacon, rollup island
and description disappear; the state icon remains, so a session awaiting your
reply or stuck in an error is still visible from another window.

Once a tool has run for 2s its name and elapsed time join the beacon
(`bash 12s`); a pending `# @steer` adds a steer icon to the model island. A
three-stop fold-view switch (`1  2  3`) highlights the selected preset for
this window; click a stop to select it, or use <leader>1..3. In the active
bar it sits to the right of the centered model island (the model name stays
centered); in an inactive bar it stays on the left. Individual folds can
still be toggled independently (|yap-folding|). Then a rollup island totals
ALL OTHER yap sessions by state: streaming, awaiting you, stopped, errored,
idle. It never counts the current buffer and folds subagents into their
parent. After the island: the session description (truncated to 40 display
columns). A provider/model island sits centered in the bar; the steer icon
sits immediately left of the model name, with a matching blank on the right
so the name stays centered. Right: two usage chips and a context-fill meter
(|yap-winbar-numbers|).

Reading the numbers                                    *yap-winbar-numbers*

  󰅐 N        Since-open: total tokens (prompt + completion) and cost for this
             buffer, accumulated since it was opened in this Neovim. Resets on
             reopen.
  󰆼 N        All-time: total tokens and cost for the whole session file,
             summed from every `turn_end` journal entry (|yap-audit|).
             Survives restarts; answers "what has this session cost".
  P% █▍░░░░  Context fill: the last turn's full prompt (including cached
             input) as a percentage of the model's context window. Colored
             green below 70%, amber 70–90%, red at 90%+.

Suffixes are compact: `k` = thousands, `m` = millions. Costs are USD, computed
as `in × input price + out × output price` (USD per 1M tokens) — your
`pricing` overrides first, then the embedded catalog (|yap-configuration|). On
a freshly opened session the two chips are equal; after a reopen they diverge.

The bar is width-aware and drops parts as the window shrinks (provider/model
island first, then the fold-view switch, then chip costs, chip tokens, then
costs and gauge percentage), re-laying out on `WinResized`. The rollup island appears whenever at least one other
session is open. For a global segment independent of yap buffers, use
`%!v:lua.require('harness').overview()` in a statusline or tabline.

10. TEMPLATES & SKILLS                                      *yap-templates*

The generic mechanism behind compaction, snippets and skills is one command:
insert a text file into the buffer. A template or a skill is just a markdown
file — the filename (minus `.md`) is the name in the picker, and the body is
what gets inserted. There is no separate serializer; the only frontmatter
schema is the optional `description:` key.

Where they live: >

  ~/.config/yap/templates/     generic text (|:YapInsert|)
  ~/.config/yap/skills/        system-prompt material (|:YapInsert|)
<
Both are configurable (`templates_dir`, `skills_dir`). Create the directory,
drop a file in, then `<C-t>` (or `:YapInsert <name>`) to insert it;
`<leader>T` inserts the raw file at the cursor.

HOW TO WRITE A TEMPLATE                                      *yap-template*

A template is generic text you want injected as a message. One rule:

  - A leading `# @role` heading (`# @user`, `# @assistant`, ...) is used as-is
    to set the role. `:Yap` already leaves an empty `# @user` prompt at the
    bottom of a session, so a template with its own `# @user` heading reuses
    that heading instead of adding a second one.
  - Otherwise the body is wrapped in `# @user` and appended at the end.

A prompt you reach for often, as a template: >

  Review the current diff for bugs and code quality. Report:

  1. Correctness issues, most severe first.
  2. Edge cases that are not handled.
  3. A simpler alternative if one is obvious.

  Be concise; reference file:line for each finding.
<
The body is wrapped in `# @user` for you, so you can leave the heading out. A
plain template is sent immediately after insertion. To prefill an assistant
reply instead, start the file with `# @assistant`.

A template containing LSP snippet syntax is expanded as a native Neovim
snippet: `$1`/`${1:placeholder}` become tabstops the cursor lands on, and
`<Tab>`/`<S-Tab>` jump between them. Snippet templates are not sent
automatically, so you can fill in the placeholders before sending with
`<C-s>`.

HOW TO WRITE A SKILL                                          *yap-skill*

A skill is instructions for the system prompt, not the message history. Its
body merges into the `# @system` message. Optional YAML frontmatter
contributes one `description:` line to the `## Skills` intro list shown in new
sessions and is stripped before merging: >

  ---
  description: Review frontend code for accessibility and semantics
  ---

  ## Frontend review

  When reviewing frontend code, check in this order:
  - accessibility: landmarks, labels, focus order, contrast
  - semantics: elements over styled divs; no nested interactive
  - type safety: no any, no @ts-ignore, no casts that hide errors

  Report findings as a list, most severe first, each with file:line and a
  one-line fix.
<
Everything after the second `---` is the body. Omitting the frontmatter is
fine. Do not include a `# @user` (or `# @assistant`) heading in a skill — it
would start a new message and split the instructions. The one exception is an
agent skill that documents the message format and quotes the headings.

WHAT INSERT DOES

  :YapInsert <template>   wrap in `# @user` and append at the end, then send
                            (unless it is a snippet; a leading `# @role`
                            heading sets the role and is never duplicated)
  :YapInsert <skill>      merge the body into `# @system`
  require('harness').insert(name, { at_cursor = true })
                            raw file above the cursor, no role logic

All insert modes go through the normal append paths; insertion never touches
existing lines. Plain templates send immediately; snippets, skills and raw
at-cursor inserts do not. While a send is in flight a template steers instead:
its body (a leading `# @role` heading stripped) is injected at the running
turn's next tool boundary as a `# @user` message, exactly like a <C-s> steer
(|yap-sessions|). Skills and raw insertion at the cursor are refused mid-turn
— they edit the buffer, which a streaming turn must not be disturbed. The
`## Skills` intro is discoverability only (names + descriptions, never skill
bodies); toggle it off with `skills_intro = false`.

COMPACTION RECIPE                                           *yap-compact*

Compaction is the template mechanism applied to a long conversation — the
summary stays a visible, editable turn, never an invisible rewrite.
|:YapCompact| automates the steps (insert, send, then offer to delete); the
manual recipe:

  1. `<C-t>` and pick `compact` — if you have not created one in templates_dir
     a built-in prompt is used. Plain templates send automatically; a
     hand-written prompt needs `<C-s>`.
  2. Delete the history above the summary (deletion = branching,
     |yap-introduction|). The summary message is the new context.
<
The archive-marker idea (folding old messages away) is deliberately NOT part
of this: the buffer is the truth, so old text is either in context or gone —
folding it away would be hidden state.

11. TOOLS & SAFETY                                              *yap-tools*

Tools are NOT configured anywhere — they are Go files in agent/tools/, one
file per tool, each self-registering in init(). Adding or changing a tool =
editing a file and recompiling (CGO_ENABLED=0). A tool returns a result (sent
to the model) and optionally a ui payload (display-only yap:ui section,
|yap-tool-region|). The binary runs the whole agent loop in one process,
bounded at 300 iterations per send.

Built-ins: ls, read, fetch, bash, python, curl, git, write, edit, search,
glob, websearch, github, playwright, quickfix, ssh, jev, close_session,
subagent, start_task, wait_tasks.

Highlights:

  - Multiple independent read-only calls in the same model round (ls, read,
    search, glob, git, fetch, websearch) execute concurrently, up to four at
    once. Yap waits for all of them and renders regions/results in call order.
    Mixed rounds and side-effecting tools retain sequential execution.
  - start_task starts bash, fetch or websearch in the background after the
    usual tool safety gate, returning a turn-local task ID. The agent can do
    independent work, then use wait_tasks with IDs (or omit IDs for all)
    to block until results are ready. At most four tasks may be outstanding.
    Do not infer success from a launch acknowledgment. Tasks cannot outlive
    the current turn: if the model tries to finish with tasks pending, Yap
    waits and gives the results to the model before the final reply. Stopping
    the turn stops tool subprocesses. The session shows launch/wait regions;
    :YapLive shows live bash output and task start/end events. Tasks do not
    persist across reopened sessions; edits and subagents cannot be started
    in the background.

  - search and glob shell out to ripgrep (rg): search returns
    path:line:content matches, glob lists files (gitignore-aware); both
    truncate to 2000 lines / 50KB.
  - websearch queries a pluggable search provider and returns up to N
    results as markdown. The provider is `websearch.provider` in
    ~/.config/yap.json (default `exa`); Exa's key is the env var named by
    `websearch.api_key_env` (default `EXA_API_KEY`). Adding a provider is
    one self-registering file in agent/tools.
  - jev is a decision model, not a language model: it answers calibrated,
    typed questions — P(yes) for yes/no, a winner + probabilities for
    pick-one, a weighted position for a scale — as probabilities, not prose.
    It backs the alert gate below and the jev tool; `decision.*` in
    ~/.config/yap.json sets its backend.
  - curl shells out to the system curl binary (method, headers, user-agent,
    body, redirects, timeout and extra flags are settable) and sends a browser
    User-Agent by default. Redirects are re-checked hop-by-hop against the
    SSRF guard; flags that could make curl a file-writer or SSRF vector
    (--unix-socket, --config/-K, -o/-O, --resolve, --connect-to, --trace*,
    --interface, ...) are refused. fetch extracts the main content as
    Markdown; curl returns the raw body and runs no JavaScript. Both accept a
    `safety` parameter: when true, the result is scanned by the decision model
    for prompt-injection content and flagged content gets an advisory warning
    line naming the probability (content is still shown, only marked). Each
    true call costs one extra decision-model round-trip.
  - git runs read-only subcommands (status, diff, log, show, blame) in the
    project root with pager, color and credential prompts disabled.
  - ssh runs non-interactive commands via the system OpenSSH client. A
    ControlMaster per user/host/port is owned by the backend (mode-0700 temp
    dir). ~/.ssh/config is disabled so aliases and proxy commands cannot
    bypass its trust boundary, and the requested host must be in NixOS's
    /etc/ssh/ssh_known_hosts. BatchMode disables interactive password/PIN
    prompts. Commands run unsandboxed over your credentials, so a dangerous
    command pauses the turn for Run/Deny.
  - quickfix replaces the quickfix list; each invocation creates a new list on
    the stack (previous reachable with |:colder| / |:cnewer|). Historical tool
    regions do not execute, so reopening a saved session never replays the
    side effect.
  - close_session asks Neovim to close the session buffer once the turn
    finishes and the file is saved. The session file is untouched, so the
    conversation stays resumable. Subagents do not get this tool.
  - write creates or overwrites files (creating parent directories); edit does
    exact-text replacement — every edits[].oldText is matched against the
    ORIGINAL file, must occur exactly once, and must not overlap another edit.
    Both return short confirmations and attach a unified diff as a
    display-only yap:ui section.
  - bash runs commands non-interactively (stdin is /dev/null) in their own
    process group: on timeout (default 120s, model-adjustable) the whole group
    is SIGKILLed, and :YapStop takes in-flight commands down with the binary.
    Output streams into a temp file and is drained into the audit view
    (|:YapLive|) — never into the session buffer. The result is truncated to
    the LAST 2000 lines / 50KB; a non-zero exit is reported, not an error.
  - python runs a Python 3 script the same way, as a fresh process (no state
    between calls). It takes exactly one of `code` (inline, run as
    `python3 <file>`) or `file` (a path to an existing script — write it first
    with the write tool, then run it). A failed script returns its traceback
    as text.
  - subagent delegates to an agent definition in ~/.yap/agents/<name>.md
    (YAML frontmatter: `name`, `model`, optional `tools`; body = system
    prompt). It creates a child session in the same project; the parent tool
    call waits for the child's answer and session path. Open and saved pickers
    show child rows; opening one lets you inspect it and ask a direct
    follow-up. Follow up through the parent with `subagent` + `session` (the
    returned path) and `task`. An agent definition without `tools` gets a
    read-only set (ls, read, search, glob, fetch, git, websearch, quickfix,
    jev); write/bash/python/curl/ssh must be requested explicitly. Delegation
    times out after ten minutes; stopping the parent stops its running child
    (the child's file is kept). There is no background spawn or child-to-child
    messaging.

Path fields on write, edit, read, ls, glob, search, git, and python (file and
cwd) — plus bash's cwd — expand a leading ~ or ~/ to the home directory.
Write larger generated scripts under ~/.yap/scratch/ (outside any project
repo) so they stay out of git.

write/edit tool headers in the buffer are SLIMMED: the arguments show
`[N lines]` / `[N edits, +A/-B lines]` instead of the content — the yap:ui
diff below shows the change, the file on disk is the ground truth, and the
full arguments are in the audit log (|yap-audit|). Every tool call and result
is also emitted as a yap:event and persisted there.

THE ALERT GATE                                        *yap-alert-gate*

Every tool call passes a pre-execution gate before it runs. Three tiers:

  silent       read, ls, glob, search, git, github, fetch, websearch, jev,
               quickfix, close_session, write, edit — run immediately.
  ask-jev      bash, python, curl, subagent, playwright — one batched
               decision-model pass decides the outcome.
  always-approval  ssh — always pauses for a Run/Deny confirmation (it keeps
               its own known-hosts check).

For `ask-jev` tools a cheap deterministic floor (destructive or high-blast-
radius commands such as `rm -rf /`, `sudo`, `curl | sh`, subprocess/os.system,
shutil.rmtree) always forces approval — the decision model never downgrades a
fork bomb. Where the floor is silent, jev answers two questions in parallel —
P(harmful) and a 0–3 severity score — and maps the answer to:

  approval   pause the turn for a Run/Deny/Inspect dialog (credential
             exfiltration, severity mean >= 2.5, destructive calls at even
             odds or low confidence, high P(harmful)). Run/Deny shows the
             reason and full call arguments, defaults to Deny, and never runs
             on timeout. Inspect focuses the shield-marked request in the
             audit; |:YapApproval| repeats Inspect or Run/Deny within five
             minutes.
  advisory   run, but log the call and show a non-blocking warning. The toast
             names the session, gives the P(harmful), the severity score
             with its category breakdown, and the model's confidence, then
             points to |:YapAlerts| for review.
  run        proceed silently.

A decision-model outage never bricks a tool: it degrades to `advisory` (a
loud warning) rather than requiring approval or running silently. Thresholds
live in the `alert` section of ~/.config/yap.json (|yap-configuration|);
defaults are conservative and tuned from the audit log. The gate is a
steerable safety net, not a security boundary: bash is unsandboxed by design —
the denylist is bypassable.

12. GLOSSARY                                                *yap-glossary*

The canonical vocabulary for yap's features and mechanisms. Use these names in
code, docs, and conversation; the right-hand column names the terms each
replaces.

  session             One conversation: its Markdown file, audit log, and
                      scratch queue. The artifact you open, name, fork, and
                      resume. (Not "chat", not "conversation".)
  session buffer      The Neovim buffer editing a session. (Not "chat
                      buffer".)
  transcript          The message text that is (re-)sent each turn — the
                      buffer's content with tool regions flattened into
                      assistant text. Distinct from the raw buffer, which also
                      holds frontmatter and marker regions.
  message             A `# @role` heading plus its body. (Not "block".)
  heading             A `# @role` line (`# @system` / `# @user` /
                      `# @assistant`).
  role                The `system` / `user` / `assistant` tag on a message.
                      Reserved for messages only.
  marker              A `<!-- yap:… -->` delimiter line. (Not "tag", "label".)
  region              A marker-delimited span — tool, thinking, error, or ui.
                      (Not "block", "detail".)
  tool region         One tool call + its result (header, result text,
                      optional yap:ui section). (Not "tool block".)
  send                The action (`:YapSend`, `<C-s>`) and the in-flight
                      request it starts.
  turn                One completed send: one assistant reply, closed by a
                      `turn_end` journal line.
  reply               The `# @assistant` message a turn produces.
  prefill             Hand-writing an `# @assistant` message so the model
                      continues from it.
  steer               Mid-turn injection of a `# @steer` body at the next
                      model boundary. Distinct from prefill.
  scratch             The file-backed `*.notes` control buffer holding
                      `# @notes` / `# @steer` / `# @queue`. (Not "jotter",
                      "sidecar".)
  audit log           The append-only `<session>.jsonl` record of every tool
                      call, result, and turn. The durable record the buffer
                      doesn't carry.
  audit view          The rendered buffer `:YapLive` rebuilds from the audit
                      log. (Not "live view", "audit drawer".)
  advisory            The gate outcome that runs a call and logs a
                      non-blocking warning. (Not "advice", "advise".)
  approval            The gate outcome that pauses a turn for a Run/Deny/
                      Inspect decision. (Not "blocked request".)
  agent definition    A `~/.yap/agents/<name>.md` file describing a subagent
                      (name, model, tools, system prompt). (Not "role",
                      "subagent role".)
  subagent            A child session spawned by the `subagent` tool from an
                      agent definition.
  decision model      The jev-style typed-probability backend behind the alert
                      gate and the `jev` tool.

"Block" survives only in standard Markdown/Vim senses unrelated to yap's
structure: code block, block-level, block comment, block device, block
element. "Blocked" as an ordinary verb (a blocked IP, a blocked read) also
remains. In yap's own structure, a foldable span is a region and a
role-delimited span is a message.
