==============================================================================
1. INTRODUCTION                                          *yap-introduction*

yap is an LLM chat plugin where the conversation lives in a plain, editable
markdown buffer. A small Go binary (`yap`) handles provider requests and the
agent/tool loop: it reads the messages on stdin and streams the reply to
stdout. There is no TUI and no hidden conversation state between turns.

To install: build the binary and put it on Neovim's PATH (see the README),
configure a provider in ~/.config/yap/settings.json, then
`require("harness").setup({...})` and run `:Yap`.

Because the buffer is the conversation, ordinary editing changes it:

- Deleting a region removes it from the conversation (branching).
- Editing an assistant reply changes what the model "said".
- Writing your own `# @assistant` message steers the model (prefill).
- Yanking, undo, folds and rendering are just Neovim; `:undotree` is a
  branch navigator.

2. SETUP & CONFIGURATION                                *yap-configuration*

Lua setup (defaults shown; substitute your own provider/model): >lua

  require("harness").setup({
    bin = "yap",                  -- path to the Go binary
    provider = "moonshot",        -- example; use your provider
    model = "kimi-k3",            -- example; use your model
    reasoning_level = "medium",  -- low | medium | high
    models = {                    -- optional: combos for the model picker
      "moonshot/kimi-k3",
      "deepseek/deepseek-v4-pro",
      "openai/gpt-5.6-sol",
    },
    system = "You are a helpful coding assistant. Answer concisely.",
    agents_file = vim.fn.expand("~/.config/yap/AGENTS.md"),
    agents_dir = "~/.config/yap/agents",       -- subagent definitions
    sessions_dir = "~/.config/yap/sessions",   -- sessions + scratch + audit logs
    templates_dir = vim.fn.expand("~/.config/yap/templates"), -- :YapInsert files
    skills_dir = vim.fn.expand("~/.config/yap/skills"),       -- system-prompt files
    notify_done = true,           -- vim.notify when a hidden turn finishes
    model_groups = {              -- named model tiers (provider/model combos)
      agent = "",                 -- session worker ("" -> provider/model above)
      editor = "deepseek/deepseek-v4-pro", -- :YapEval one-shot
      title = "",                 -- session titles ("" disables titling)
    },
    syntax_highlight = true,      -- keep markdown syntax colors
    nerd_font = true,             -- false for plain-Unicode icons
    icons = { since = "󰅐", total = "󰆼" }, -- winbar/picker glyph overrides
    keymaps = { stop = "<C-c>" }, -- override any key; "" disables it
  })
<

`agents_file` is the system prompt for new buffers, read per buffer (edits
apply to the next session). When missing or empty, `system` is used. The path
is used verbatim (no `~` expansion); the default is `$XDG_CONFIG_HOME/yap/AGENTS.md`
(or `~/.config/yap/AGENTS.md`).

`agents_dir` and `sessions_dir` locate yap's data under the XDG config home —
`$XDG_CONFIG_HOME/yap/` (default `~/.config/yap/`); a leading `~` resolves
to your home directory, an absolute path is used verbatim.

`notify_done` (default true) fires `vim.notify` when a turn completes in a
buffer not visible in any window. The turn's `turn_end` payload (model,
tokens, cost, ms) is also emitted on the `User YapTurnDone` autocmd so other
plugins can hook completion (e.g. noice/nf-notify rendering, or chaining a
next send). Disable with `notify_done = false` and hook that event yourself.

`syntax_highlight` (default true) keeps tree-sitter markdown highlighting;
set false to drop syntax colors.

`nerd_font`/`icons` control the winbar and picker glyphs (|yap-winbar|).
Icon keys include `since`, `total`, `running`, `waiting`, `stopped`, `error`,
`idle`, `done`, `steer`, `approval`, `cap_l`, `cap_r`. Defaults are Nerd Font
v3 glyphs; `nerd_font = false` selects plain-Unicode icons, the typographic
spinner and the block gauge. Explicit `icons` entries win; set one to `""` to
drop it.

`model_groups` is the single place every model-using feature reads its
"provider/model" combo from, so a tier is set once and every feature that uses
it follows:

  agent  — the session worker. Empty falls back to `provider`/`model` above
           (and a persisted |:YapChangeDefaultModel| still wins over both).
  editor — the one-shot, no-tools model behind |:YapEval|.
  title  — session titling: both the instant on-send label and the final
           whole-session summary.

Set a group to `""` to disable it. `title` defaults to `""` (titling off);
set it to a cheap combo like `deepseek/deepseek-flash` to label sessions. An
empty `editor` group makes |:YapEval| inherit the buffer's current combo (a
session's model, or the setup() default for a plain buffer); it defaults to
`deepseek/deepseek-v4-pro`. A `title:` you type in the frontmatter wins over
the `title` group.

`reasoning_level` (`low`/`medium`/`high`) is seeded into every new
session's frontmatter so it is visible and hand-editable from the first
line. Delete the line in a session to fall back to the provider's own
default. `reasoning_level` is a cross-provider effort knob:
it maps to OpenAI's `reasoning.effort`, Anthropic's `effort`/thinking budget,
Gemini's `thinkingLevel`, and DeepSeek has no equivalent (ignored).

`keymaps` maps each action in |yap-keymaps| to its key; set one to `""` to
disable it. `templates_dir`/`skills_dir` configure
|yap-templates|.

Config and data files (defaults shown; the config home is
`$XDG_CONFIG_HOME/yap` — `~/.config/yap` unless `$XDG_CONFIG_HOME` is set —
and each path is configurable via `setup()` / the Nix module options):

  ~/.config/yap/settings.json   Providers: >json

  {
    "providers": {
      "moonshot": {
	"base_url": "https://api.moonshot.ai/v1",
	"api_key_env": "MOONSHOT_API_KEY"
      }
    },
    "decision": {
      "provider": "jev",
      "base_url": "https://openrouter.ai/api/alpha/decisions",
      "api_key_env": "OPENROUTER_API_KEY",
      "model": "typesafe/jev-1.13"
    },
    "alert": {
      "approval_prob": 0.7,
      "advisory_prob": 0.25,
      "min_confidence": 0.6
    },
    "ssh": {
      "known_hosts": "~/.ssh/known_hosts"
    }
  }
<
  Supported providers (the provider name is the key under "providers"):

    name        base_url                                  api_key_env example
    openai      native; default https://api.openai.com/v1  OPENAI_API_KEY
    anthropic   native; default https://api.anthropic.com  ANTHROPIC_API_KEY
    google      native; default Google Generative Language GEMINI_API_KEY
    gemini      alias of google                            GEMINI_API_KEY
    deepseek    native; default https://api.deepseek.com   DEEPSEEK_API_KEY
    <other>     REQUIRED; any OpenAI-compatible endpoint   e.g. MOONSHOT_API_KEY,
                (moonshot https://api.moonshot.ai/v1,      OPENROUTER_API_KEY
                openrouter https://openrouter.ai/api/v1,
                z.ai, local servers, ...)

  Native providers need no `base_url` (set one only for a proxy; Anthropic's
  takes no `/v1`, Google's no `/v1beta`). Direct Anthropic ids use dashes
  (`claude-sonnet-5-5`), OpenRouter's dots. API keys come from the named env
  vars; the github tool reads `GITHUB_TOKEN` directly. Prices come from
  `agent/price/pricing.json`.

  `decision` configures the backend behind the decision tool and alert gate
  (|yap-alert-gate|): `provider` (default "jev"), `base_url`, `api_key_env`,
  `model`. `alert` tunes the gate thresholds.
  `ssh.known_hosts` overrides the file the ssh tool checks hosts against.

  ~/.config/yap/AGENTS.md  Default system prompt (see above).
  ~/.config/yap/templates/ |:YapInsert| template files (|yap-templates|).
  ~/.config/yap/skills/    |:YapInsert| skill files (|yap-templates|).
  ~/.config/yap/sessions/  Autosaved sessions + scratch queues + audit logs.
  ~/.config/yap/agents/    Subagent definitions.

3. COMMANDS                                                  *yap-commands*

Commands act on the current buffer unless otherwise noted. They are quiet on
success: visible edits, the winbar and pickers confirm ordinary actions.

*:Yap*
:Yap                  Open a new session buffer with a system message and an
                        empty `# @user` prompt. Nothing is sent until you type
                        there and |:YapSend|.
*:YapSend*
:YapSend              Send the whole buffer to the provider and stream the
                        reply in. Also appends Neovim's current working
                        directory and git snapshot as request-only context
                        (evaluated at send time), so `:cd` takes effect on
                        the next send.
*:YapStop*
:YapStop              Kill the in-flight request for the current buffer.
*:YapLive*
:YapLive              Open this session's live tool tail (|yap-audit|): one
                        persistent, read-only buffer following the running
                        tool's output — a `$ command` header per bash call with
                        its streamed output. Opens scrolled to the bottom (or
                        focuses the existing window); `q` closes it.
*:YapGuard*
:YapGuard            Open the guard board (yap://guard): a read-only bottom
                        drawer of approvals and advisories (|yap-alert-gate|).
                        <Tab>/`za` expand a row; on the
                        row under the cursor `r`/`x` run/deny an approval, `i`
                        inspects, `c` clears every guard and advisory item,
                        `q` closes.
*:YapClear*
:YapClear [keep]      Replace the result bodies of all but the last [keep]
                        (default 2) yap:tool regions with a one-line
                        placeholder naming the audit-log lines
                        (path:line-range) where the removed output lives.
                        Full output stays in the audit log (|yap-audit|).
*:YapCompact*
:YapCompact           Insert the compact prompt (a `compact` template, or a
                        built-in prompt), send, and — once the summary has
                        streamed in — offer to delete the superseded history
                        (|yap-compact|).
*:YapEval*
:YapEval [instruction]
                        Open an interactive eval session in a split about
                        the selected lines (or about the current file with no
                        range). It is a regular session (default system
                        prompt, tools, follow-ups), listed in |:YapHistory|.
                        The selection is quoted as context and the
                        source buffer is never changed. With an instruction
                        the first turn is sent at once; without one the
                        cursor waits in the user turn for your question.
:YapEval! [instruction]
                        Replace the selected lines with the model's output: a
                        one-shot, no-tools call to the `editor` model group. Acts on a
                        linewise range (a visual selection via `:'<,'>` or an
                        explicit `:1,5`); with a selection and no instruction
                        it applies a default transform ("Improve this text"),
                        and with no range it prompts for one. In a yap buffer
                        the replacement is wrapped as a single `# @assistant`
                        message (select a run of turns
                        to summarize them); in any other buffer it is plain
                        text (refactor a function in place). With no range,
                        the output is inserted at the cursor as new lines
                        (generate content into a fresh, empty buffer). No
                        default keymap for either form.
*:YapInsert*
:YapInsert [name]     Insert a template or skill (|yap-templates|). With no
                        argument, pick from a combined list. At the cursor,
                        use `<leader>T`.
*:YapChangeModel*
:YapChangeModel {provider/model}
                        Change this buffer's provider/model combo. Without an
                        argument, pick from a list. Mid-turn, the new combo
                        takes effect at the next model boundary. To change
                        the default for new buffers, use `<leader>M`.
*:YapFork*
:YapFork [name]       Copy the current in-memory conversation into a new,
                        independent session in the same project. The original
                        buffer, file and running state stay attached to the
                        original; the copy opens in the current window. No
                        name generates a filename; a name uses `name.md`.
                        Existing files are never replaced.
*:YapHistory*
:YapHistory [scope]   Pick a saved session to resume. scope is `cwd` (the
                        default, current project) or `all` (every project).
                        Open sessions are unlisted (use `<leader>r`).

4. KEYMAPS                                                    *yap-keymaps*

Set only in yap buffers, except <leader>r, <leader>w, <leader>y, <leader>g
and <leader>M, which are global. Every binding is a `keymaps` config key
(see |yap-configuration|); the defaults are shown below.

  <C-s> (n, i)          Send the buffer. The reply streams in.
  <C-c>                 Kill the in-flight request (see |:YapStop|).
  <leader>m             Change model (picker, see |:YapChangeModel|).
  <leader>M             Change the default model for new buffers (picker).
  <leader>g             Open/close the guard board (see |:YapGuard|).
  <leader>l             Watch the live tool tail (see |:YapLive|).

Inside the guard board, <leader>l opens the live tail directly below it;
inside the live tail, <leader>g opens the guard board directly above it.
Both bindings are present in every yap panel (session, guard, live tail and
scratch), so the two stay stacked in the fixed session → guard → log order
regardless of which one you open first.
  <leader>s             Toggle the scratch buffer (see |yap-sessions|).
  <C-t> (n, i)          Insert a template or skill (see |:YapInsert|).
  <leader>T             Insert a template or skill at the cursor.
  <C-f> (i)             Pick a file under the current |:pwd| and insert an
                        `@path` reference at the cursor (resumes insert mode).
  <leader>r             Pick an open session.
  <leader>w             Pick a session awaiting a reply or manually stopped.
  <leader>y             Pick a saved session to resume.
  g?                    Show the current Yap shortcuts in a searchable
                        floating window; use `/`, `n` and `N`.
  <Tab>                 Toggle the fold under the cursor.
  ]m  [m                Next / previous message heading.
  ]u  [u                Next / previous user message.
  ]a  [a                Next / previous assistant message.
  ]t  [t                Next / previous tool call or thinking region (opens it).
  ]c  [c                Next / previous thinking region (opens it).
  ]e  [e                Next / previous error region (opens it).
  ]]  [[		Next # heading (default Neovim markdown behavior)

  <leader>1             Fold all agent messages; user prompts stay open.
  <leader>2             Fold all tool calls and thinking regions.
  <leader>3             Unfold everything.

  Text objects (operator-pending and visual mode):
    im / am             inner / a message — the body without its `# @role`
                        heading, or the whole message. `cim` replaces a
                        message body; `dam` drops a message.
    it / at             inner / a thinking, tool or error region — the content
                        without its markers, or the whole region.

View 2 is the default; the system prompt stays folded in views 1 and 2
(|yap-folding|).

5. BUFFER FORMAT                                                *yap-buffer*

A yap buffer is plain markdown. Headings delimit messages: >

  # @system
  # @user
  # @assistant
<

Everything between headings is message content. Everything before the first
heading is ignored by the parser — that is where the session's state lives,
as YAML frontmatter: >

  ---
  title: Fix the session picker
  description: Fix session picker labels and summaries
  model: kimi-k3
  provider: moonshot
  reasoning_level: high
  created_cwd: ~/code/project
  turns: 14
  created_at: 2025-09-29T19:22:33Z
  updated_at: 2025-09-29T19:24:01Z
  models:
    - moonshot/kimi-k3
    - deepseek/deepseek-v4-pro
  subagents:
    - ~/.config/yap/sessions/.../session-a1b2c3.md
  tools:
    - read
    - search
    - glob
  assets:
    - ~/.local/share/nvim/yap/assets/<sha256>.png
  ---
<

`title` (always present, empty by default) overrides `description` as the
session's display name. `description` is the generated summary shown while the
title is empty. `provider`/`model` is the combo to resume with;
`reasoning_level` (`low`/`medium`/`high`) is a sampling knob, seeded from
the setup() defaults on new sessions and hand-editable like `tools`, read
on every send; `created_cwd`
the exact working directory the session was created in; `models` the ordered
history of combos used (most-recent-last); `subagents` the subagent session
paths; `tools` the per-session tool allowlist — remove a line to retract that
tool on the next send; `assets` the absolute paths of the photo files this
session references (a shared content-addressed store under Neovim's data
directory). `turns` counts completed `# @assistant` replies so
the picker can show depth without opening the file.

The active combo comes from the frontmatter on open, then per-buffer vars set
by |:YapChangeModel|, then the persisted default, then setup() defaults.
Legacy files without frontmatter keep the setup() default combo.

6. MARKERS & TOOL REGIONS                                      *yap-markers*

HTML comment regions of the form `<!-- yap:<word>` ... `-->` appear in the
buffer but are never sent to the provider as buffer text:

  <!-- yap:thinking   Provider-exposed reasoning (or summaries), streamed in.
                        Folded away with the assistant message.
  <!-- yap:error      Backend error record, left after a failed send.
  <!-- yap:usage      Token usage at end of stream; consumed into the winbar
                        totals and removed.

Tool regions                                                *yap-tool-region*

A tool call and its result are ONE region inside an assistant message: >

  <!-- yap:tool {"id":"call_1","name":"edit","arguments":{...}} -->
  Successfully replaced 1 edit(s) in main.go.
  <!-- yap:ui -->
  ```diff
  @@ -10,3 +10,3 @@
  -old line
  +new line
  ```
  <!-- /yap:ui -->
  <!-- /yap:tool -->
<

  Header          The call as JSON. Short headers are single-line; longer
                  ones are pretty-printed between `<!-- yap:tool` and `-->`
                  and fold closed by default.

  Result text     What the model received. edit/write tools return short
                  confirmations; read-like tools return (truncated) content.
                  The header normally lands BEFORE the tool runs, so its
                  arguments are visible during execution. Live bash output is
                  followed via |:YapLive|, never written into the buffer.

  <!-- yap:ui   Optional display-only diff for edits and writes, fenced as
                  ```diff between paired one-line markers. It is pure
                  decoration — editing or deleting it changes nothing.

The region is flattened into assistant transcript text (tool name, JSON
arguments, result) when the buffer is sent. Editing or deleting the visible
markdown changes the transcript directly; a region outside an assistant
message is skipped.

Tool results from content-bearing tools (read, bash, ls, fetch, curl, git,
search, glob) are wrapped in a fenced code block — read with a language info
string detected from the path, fetch as ```markdown, the rest plain.
write/edit return short confirmations and stay bare.

7. SESSIONS                                                  *yap-sessions*

A session is the conversation markdown file plus a few sidecar files: an
append-only audit log, an optional scratch notes file, and photo attachments
in a shared asset store. Each session lives in its own directory,
~/.config/yap/sessions/<cwd-slug>/<session>/, containing session.md (the
conversation), audit.jsonl (the audit log) and notes.md (the scratch jotter).
Sessions are saved after every turn; the file is created when the buffer
opens, and every save goes through |:write| so 'modified', |:w| and the exit
prompt behave normally.

Opening a session file directly — plain |:edit| or `nvim <file>.md` — adopts
it as a managed session (unlisted, keymapped, live tool tail attached), the same
as |:YapHistory| resume.

File operations are the session operations:

  edit the `title:` line  Type a value after the always-present, empty
                         `title:` key to name the session; leave it empty for
                         the generated description to win.
  |:YapFork|              Copy the conversation into a new session directory.
  delete a region + send  Branch the conversation within the active session.

SCRATCH BUFFER

<leader>s toggles the scratch buffer — a file-backed sibling (`notes.md`)
with three independently foldable sections:

  # @notes    An inert backlog; never sent.
  # @steer    A replaceable pending message for the RUNNING turn. <C-s>
              submits it; it stays until delivered and can be revised or
              canceled. If it misses the last model boundary or the turn is
              stopped, it remains a draft (never auto-sent).
  # @queue    Sent whole as one message on <C-s> while idle, cleared only
              after the send starts. Never auto-dispatches after a turn.

AUDIT LOG                                                        *yap-audit*

audit.jsonl beside the session file is an append-only, JSON Lines record that
survives restarts: every tool call (full arguments), full tool results, image
attachments, approval/advisory decisions, a retry line for each transient
generation error, and one `turn_end` line per completed send (model, prompt,
completion, cost, ms).

The live tool tail (|:YapLive|) is a separate, plain buffer that follows the
running tool's output — a `$ command` header per bash call plus its streamed
bytes. It is never rebuilt from the audit log; the full streamed output lives
in the tool's temp log, and the audit log carries the tail-truncated result.
|:YapGuard| lists advisories and approval requests and jumps to the matching
tool region in the session. |:YapClear| placeholders point back at the exact
audit-log lines they replaced.

The session directory is kept mode 0700 and its files mode 0600 — transcripts
and tool output routinely contain secrets.

8. FOLDING & NAVIGATION                                        *yap-folding*

`# @role` headings are folds; a closed fold shows the role and the first
content line. A whole yap:tool region folds to one `▸ tool: <name>` line;
thinking and error comment regions fold likewise. The YAML frontmatter folds
to a single `▸ options` line.

Three views, bound to <leader>1..3:

  <leader>1   only user prompts stay open
  <leader>2   conversation open, tool calls and thinking folded (default)
  <leader>3   everything unfolded

The system prompt and the frontmatter stay folded in views 1 and 2 and open
with everything else in view 3 (or earlier with za). Each window owns its
selected view and open/closed choices; a view keypress resets this window's
choices only.

<Tab> toggles the region under the cursor. ]t/[t, ]c/[c and ]e/[e jump to and
open a region without closing earlier ones. Clicking a closed fold opens it
(the same choice as <Tab>); native za/zo/zc, zA/zO/zC and zR/zM/zr/zm share
the same state. ]m/]u/]a only navigate. Message navigation and the message
text objects follow the same structural parse as folding, so a `# @user` line
inside a fenced tool result is literal content, never a message boundary.

9. WINBAR                                                      *yap-winbar*

The winbar is the session dashboard. Left: the buffer's own state icon —
idle, awaiting your reply, stopped, error, or done (a finished subagent) — in
the line-number gutter; while streaming, an animated beacon that escalates
with how long the running tool has been grinding. When the window is inactive
the beacon and title disappear; the state icon remains.

Once a tool has run for 2s its name and elapsed time join the beacon
(`bash 12s`); a pending `# @steer` adds a steer icon. A three-stop fold-view
switch (`1  2  3`) highlights the selected preset; click a stop or use
<leader>1..3. Then a rollup island totals ALL OTHER yap sessions by state
(streaming, awaiting you, stopped, errored, idle). After the island: the
session title (the `title:` frontmatter value when set, else the generated
description), truncated to 40 display columns. A provider/model island sits
centered in the bar. Right: two usage chips and a context-fill meter.

Reading the numbers                                    *yap-winbar-numbers*

  󰅐 N        Since-open: total tokens (prompt + completion) and cost for this
             buffer, accumulated since it was opened in this Neovim. Resets on
             reopen.
  󰆼 N        All-time: total tokens and cost for the whole session file,
             summed from every `turn_end` journal entry (|yap-audit|).
             Survives restarts; answers "what has this session cost".
  P% █▍░░░░  Context fill: the last turn's full prompt as a percentage of the
             model's context window. Green below 70%, amber 70–90%, red 90%+.

Suffixes: `k` = thousands, `m` = millions. Costs are USD, computed from the
committed catalog (`agent/price/pricing.json`). On a freshly opened session
the two chips are equal; after a reopen they diverge. The bar is width-aware
and drops parts as the window shrinks.

For a global segment independent of yap buffers, use
`%!v:lua.require('harness').overview()` in a statusline or tabline.

10. TEMPLATES & SKILLS                                      *yap-templates*

A template or skill is just a markdown file — the filename (minus `.md`) is
the name in the picker, the body is what gets inserted. They live in:

  ~/.config/yap/templates/     generic text (|:YapInsert|)
  ~/.config/yap/skills/        system-prompt material (|:YapInsert|)

Both configurable via `templates_dir` / `skills_dir`. Create the directory,
drop a file in, then `<C-t>` (or `:YapInsert <name>`) to insert it;
`<leader>T` inserts the raw file at the cursor.

HOW TO WRITE A TEMPLATE                                      *yap-template*

A template is generic text you want injected as a message:

  - A leading `# @role` heading (`# @user`, `# @assistant`, ...) sets the
    role and is used as-is (a `# @user` heading reuses the existing trailing
    prompt instead of adding a second one).
  - Otherwise the body is wrapped in `# @user` and appended at the end.

A prompt you reach for often, as a template: >

  Review the current diff for bugs and code quality. Report:

  1. Correctness issues, most severe first.
  2. Edge cases that are not handled.
  3. A simpler alternative if one is obvious.

  Be concise; reference file:line for each finding.
<
A plain template is sent immediately after insertion. To prefill an assistant
reply instead, start the file with `# @assistant`.

A template containing LSP snippet syntax is expanded as a native Neovim
snippet: `$1`/`${1:placeholder}` become tabstops, `<Tab>`/`<S-Tab>` jump
between them. Snippet templates are not sent automatically.

HOW TO WRITE A SKILL                                          *yap-skill*

A skill is instructions for the system prompt, not the message history. Its
body merges into the `# @system` message. Optional YAML frontmatter
contributes one `description:` line to the `## Skills` list in the About Yap
prefix (refreshed on every send) and is stripped before merging: >

  ---
  description: Review frontend code for accessibility and semantics
  ---

  ## Frontend review

  When reviewing frontend code, check in this order:
  - accessibility: landmarks, labels, focus order, contrast
  - semantics: elements over styled divs; no nested interactive
  - type safety: no any, no @ts-ignore, no casts that hide errors

  Report findings as a list, most severe first, each with file:line and a
  one-line fix.
<
Everything after the second `---` is the body. Omitting the frontmatter is
fine. Do not include a `# @user` (or `# @assistant`) heading in a skill — it
would start a new message and split the instructions.

WHAT INSERT DOES

  :YapInsert <template>   wrap in `# @user` and append at the end, then send
                            (unless a snippet; a leading `# @role` heading
                            sets the role and is never duplicated)
  :YapInsert <skill>      merge the body into `# @system` (and reveal it)
  require('harness').insert(name, { at_cursor = true })
                            raw file above the cursor, no role logic

Plain templates send immediately; snippets, skills and raw at-cursor inserts
do not. While a send is in flight a template or skill steers instead: its body
(a leading `# @role` heading stripped) is injected at the running turn's next
tool boundary as a `# @user` message, exactly like a <C-s> steer
(|yap-sessions|). Raw insertion at the cursor is refused mid-turn.
The `## Skills` section of the About Yap prefix lists names + descriptions,
refreshed on every send.

COMPACTION RECIPE                                           *yap-compact*

|:YapCompact| automates compaction (insert, send, then offer to delete); the
manual recipe:

  1. `<C-t>` and pick `compact` — if you have not created one in templates_dir
     a built-in prompt is used. Plain templates send automatically; a
     hand-written prompt needs `<C-s>`.
  2. Delete the history above the summary (deletion = branching,
     |yap-introduction|). The summary message is the new context.

11. THE ALERT GATE                                        *yap-alert-gate*

Every tool call passes a pre-execution gate. Three tiers:

  silent           read, ls, glob, search, git, github, fetch, websearch, decision,
                   quickfix, close_session, write, edit — run immediately.
  ask-model        bash, python, curl, subagent, playwright — a decision-model
                   pass decides the outcome.
  always-approval  ssh — always pauses for a Run/Deny confirmation.

For `ask-model` tools a deterministic floor (destructive or high-blast-radius
commands such as `rm -rf /`, `sudo`, `curl | sh`, `subprocess`/`os.system`,
`shutil.rmtree`) always forces approval. Where the floor is silent, the
decision model answers three questions in one pass — P(harmful), a 0–3 severity
score, and P(reveals a live secret value) — and maps the result to:

  approval   pause the turn for a Run/Deny/Inspect decision (|:YapGuard|).
             Never runs on timeout (five minutes) or when the board is
             dismissed. A call that would reveal a live secret or credential
             value forces approval even when severity reads benign.
  advisory   run, but log the call to the guard board's Advisory section
             (no notification) with a plain-language risk phrase — audit it
             later in |:YapGuard|, which keeps the numbers.
  run        proceed silently.

A decision-model outage degrades to `advisory` rather than blocking. Thresholds
live in the `alert` section of config.json (|yap-configuration|). The gate is
a steerable safety net, not a security boundary: bash is unsandboxed by
design — the denylist is bypassable.

12. GLOSSARY                                                *yap-glossary*

The canonical vocabulary for yap's features and mechanisms. Use these names in
code, docs, and conversation; the right-hand column names the terms each
replaces.

  session             One conversation: its Markdown file, audit log, and
                      scratch queue. The artifact you open, name, fork, and
                      resume. (Not "chat", not "conversation".)
  session buffer      The Neovim buffer editing a session. (Not "chat
                      buffer".)
  transcript          The message text that is (re-)sent each turn — the
                      buffer's content with tool regions flattened into
                      assistant text. Distinct from the raw buffer, which also
                      holds frontmatter and marker regions.
  message             A `# @role` heading plus its body. (Not "block".)
  heading             A `# @role` line (`# @system` / `# @user` /
                      `# @assistant`).
  role                The `system` / `user` / `assistant` tag on a message.
                      Reserved for messages only.
  marker              A `<!-- yap:… -->` delimiter line. (Not "tag", "label".)
  region              A marker-delimited span — tool, thinking, error, or ui.
                      (Not "block", "detail".)
  tool region         One tool call + its result (header, result text,
                      optional yap:ui section). (Not "tool block".)
  send                The action (`:YapSend`, `<C-s>`) and the in-flight
                      request it starts.
  turn                One completed send: one assistant reply, closed by a
                      `turn_end` journal line.
  reply               The `# @assistant` message a turn produces.
  prefill             Hand-writing an `# @assistant` message so the model
                      continues from it.
  steer               Mid-turn injection of a `# @steer` body at the next
                      model boundary. Distinct from prefill.
  scratch             The file-backed `notes.md` control buffer holding
                      `# @notes` / `# @steer` / `# @queue`. (Not "jotter",
                      "sidecar".)
  audit log           The append-only `audit.jsonl` record of every tool
                      call, result, and turn. The durable record the buffer
                      doesn't carry.
  audit view          The live tool tail `:YapLive` opens: one read-only
                      buffer per session following the running tool's output.
                      (Not "live view", "audit drawer".)
  advisory            The gate outcome that runs a call and logs a
                      non-blocking warning. (Not "advice", "advise".)
  approval            The gate outcome that pauses a turn for a Run/Deny/
                      Inspect decision. (Not "blocked request".)
  agent definition    A `~/.config/yap/agents/<name>.md` file describing a subagent
                      (name, model, tools, system prompt). (Not "role",
                      "subagent role".)
  subagent            A child session spawned by the `subagent` tool from an
                      agent definition.
  decision model      The typed-probability backend behind the alert
                      gate and the `decision` tool.

"Block" survives only in standard Markdown/Vim senses unrelated to yap's
structure: code block, block-level, block comment, block device, block
element. "Blocked" as an ordinary verb (a blocked IP, a blocked read) also
remains. In yap's own structure, a foldable span is a region and a
role-delimited span is a message.
