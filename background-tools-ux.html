Background tools in Yap

Design proposal, not current behavior. Yap currently executes multiple tool calls from one model response sequentially. Its tool region opens before execution and closes when the result arrives.

What the user would see

Keep the session Markdown as a chronological record. A background launch gets a short, completed tool region containing a task ID. Do not leave a tool region open while unrelated conversation is appended.

Assistant: I'll start the tests and inspect the implementation meanwhile.

▸ tool: start_task
  Started task 12: tests (running).

▸ tool: read
  …file contents…

Assistant: The parser needs one change. I'll check the test result.

▸ tool: wait_tasks
  Task 12 finished: exit 0. 84 tests passed.

The examples above are the visible, folded presentation, not literal Yap marker syntax. Opening a region would reveal the call arguments and result as usual. :YapLive would show task 12's progress and full output while it runs. A background subagent would remain an inspectable child session.

A compact task indicator in the winbar could show 2 running; completion could change it to 1 ready. This is a status indicator, not a notification that forces focus away from the editor.

Rendering rule: completion does not insert text back into the earlier “Started” region. The final result appears at the next explicit wait or at a defined model boundary. Otherwise late output could rearrange an editable transcript beneath the user's cursor.

What could be brittle

AreaFailure modeUX requirement
Transcript and replay Yap's buffer is the saved conversation. A visible “running” task might be edited, deleted, forked, or reopened after its process has gone away. Never infer a live task solely from Markdown. A missing task must produce a clear “no longer available” result, not hang.
Native tool results A normal tool call expects its result before the next model step. Acknowledging a launch is not the original operation's final result. Use an explicit launch-and-wait contract unless a provider supports genuine async calls. Do not present “started” as “tests passed.”
Concurrent output Two workers writing session text or audit events at once could interleave headers, results, or log lines. Yap's current live-tool state also describes one running tool per session. Workers produce events tagged with task IDs; one owner serializes writes to the session and audit view.
Approvals and side effects A generic background launcher could bypass a tool's safety gate, or run an approved operation later when circumstances have changed. Concurrent edits can conflict. Apply the original tool's gate before dispatch. Initially restrict background execution to non-conflicting work.
Stopping and closing :YapStop, a closed buffer, or a backend restart could leave processes or subagents running without an owner. Define cancellation and cleanup before exposing the feature. Show stopped, failed, and timed-out states distinctly.
Subagents Yap currently tracks one running child per parent. Multiple children need independent IDs, callbacks, results, and ownership; one child's completion must not consume another's reply. Show each child separately and retain its saved session link.
Finishing early The assistant can produce a convincing final answer while checks are still running—or poll repeatedly and waste tokens. Before finalizing, surface outstanding tasks once and require an explicit wait or explicit decision to leave them running. Prefer a blocking wait over busy polling.
Result size and trust Background logs may be huge or contain untrusted text and secrets. Keep the existing truncation, scrubbing, and audit behavior; return a bounded result to the model with a way to inspect the full log.

A safer first version

  1. Allow several independent, same-response read-only calls to run in parallel, but return all results before the next model step. This changes latency without changing transcript semantics.
  2. Add turn-scoped background tasks for long-running, non-conflicting work. Launch returns an ID; wait_tasks returns results. Serialize all visible text on the main session writer.
  3. Only after that works reliably, consider tasks that survive a turn. They require durable task state, restart behavior, notifications, and a decision about what happens when a session is forked.

Key UX principle: the session must never imply that a pending operation succeeded. “Started,” “running,” “finished,” “failed,” and “lost” should be visibly different states.
